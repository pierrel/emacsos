* IN FLIGHT: Voice-call assistant (paused at P3 power gate)

*The big current initiative* — dial the SIM and talk to assist by voice: a
PIN-gated *receptionist* agent helps you reach a thread (or start one with a
domain), then a natural voice conversation inside it. It sidesteps the iOS-Safari
background-audio blocker entirely (a real call; the OS owns it) and builds on the
*already-validated* SIM7600G-H telephony substrate.

* TODO PinePhone minimal client with reliable deep sleep

Use the PinePhone as the first integrated Assist smartphone testbed, but replace
the general-purpose Phosh desktop with the smallest useful awake surface: a
minimal Wayland compositor, PGTK Emacs, phone primitives, and the Assist client.
Firefox and Waydroid make a compositor non-optional; they run as on-demand
full-screen clients rather than turning EmacsOS back into a desktop.  Removing
the Phosh/GNOME shell should improve responsiveness and reduce awake overhead,
but it is explicitly *not* the battery strategy by itself.

Battery life depends on making Crust deep suspend reliable.  The intended power
model is:
- while awake, run only the minimal Emacs UI and services required for phone
  operation;
- turn the display off automatically and enter deep suspend when idle;
- leave the cellular modem registered, with its ring indicator able to wake the
  application processor for incoming calls and SMS;
- keep canonical Assist execution on the always-on server, then reconnect the
  phone client after wake instead of keeping the phone CPU and a network socket
  awake continuously;
- treat calls, SMS, and alarms as wake-capable.  Ordinary internet notifications
  are not assumed to arrive during deep sleep; any Assist-initiated urgent wake
  needs an explicit call/SMS path or must wait for the next wake.

Field evidence from postmarketOS edge on the PinePhone 1.2 (2026-08-30): with
automatic display blanking disabled for diagnosis and the phone kept awake, the
battery reported about 1.04 A at 3.87 V (roughly 4 W), consistent with only a few
hours of runtime.  A separate failure occurred after Phoc turned the display off:
the phone stopped logging and became unreachable, with no recorded suspend,
power-key event, kernel panic, GPU error, OOM, or clean shutdown.  Do not paper
over that failure with a lighter UI; prove the new display-off and suspend/resume
path directly.

The v26.06/OpenRC control captured a kernel RCU stall after USB power removal,
so it is rejected for this experiment.  The active v25.06/OpenRC/6.13.8 image
has passed a multi-hour plugged run with Sway, PGTK Emacs, wvkbd, handset audio,
Firefox, on-demand Waydroid, repeated DPMS, and intentional UI failure recovery.
Pierre's first unplugged hands-on run, physical display-off/wake, and an
RTC-driven deep suspend passed with the same Sway and Emacs processes.  During
unattended integration, only the reviewed 60-second display blank is installed;
the kernel-suspend helper and UI suspend privilege are removed so the phone
remains remotely recoverable.  Four
plugged automatic RTC-wake cycles passed under the former suspend policy.  The
three post-fix captures were clean, including a 23-minute-33-second unreachable
interval between kernel suspend entry and RTC wake, followed by visible Firefox
and Android browser smokes.  The next gates are duration and battery runs,
followed by modem validation with Pierre present.
Firefox/Android authority
separation and restrictive guest networking remain gates before untrusted
Android apps.  Detailed evidence and rejected
hypotheses are in [[file:docs/2026-08-31-pinephone-emacsos-session.org][the session record]];
verified images and fallback procedure are in
[[file:docs/2026-09-01-pinephone-base-recovery.org][the base-recovery record]].

Acceptance is repeated unplugged display-off/deep-suspend/resume cycles with
working calls and SMS wake, clean modem and network recovery, Assist reconnection,
and materially lower measured standby drain.  Also test the charging case
separately because PinePhone USB-C/display interactions have already produced
different behavior in live use.

The staged direct-computer architecture, automatic screenshot/input/suspend
harness, authenticated lab recovery, later locked fallback, promotion gates,
and stop conditions are in
[[file:docs/2026-08-31-pinephone-emacsos-session.org][2026-08-31-pinephone-emacsos-session.org]].

** DONE Ctrl/Meta modifier keys

Shipped on the =modifier-keys= branch: a leftmost MOD button on the
action row cycles =nil → C → M → C-M → nil=; under a non-nil
modifier, the T9 grid filters to letters that have a binding under
the current modifier in the target buffer's full active-keymap stack
(via =key-binding=), and a tap *fires* the bound command instead of
inserting a letter.  Single-letter fast-path (one bound letter →
fire on tap, no wait); multi-letter subset → arm-then-commit with
multi-tap cycling.  Sticky modifier (only an explicit MOD tap
changes it).  QUIT abandons an armed binding; every other utility
tap commits it.  Shift was rolled into the existing CAPS (locked
decision; under MOD, caps is ignored and canonical lowercase keys
go to the keymap walker).  Full design + decisions in
[[file:docs/2026-05-27-modifier-keys.org][2026-05-27-modifier-keys.org]].

** TODO Font choice + sizing

The default emacs face on the phone is whatever the system X
fontconfig defaults pick — not optimized for a 320x240 surface
held at arm's length.  Pick a font (and sizes for transcript /
input / keyboard / status) that reads well at this density:
legibility at small px counts, distinguishable lowercase l vs.
uppercase I vs. digit 1, comfortable line-height in =*chat*=.
Candidates: a programming font (Iosevka, JetBrains Mono) tuned
for clarity at small sizes, or a screen-optimized humanist like
Inter.  Try a couple, decide on the phone, codify in =os.el=
(or a per-face block in the init snippet) so phone-install
sets it consistently.

* Tool-call transparency

The emacs-modifying channel ships with `status: calling <tool_name>`
events for each new tool invocation.  Intended UX was richer
(`status: <tool_name>: <truncated args>`) but the implementation
needs `tool_call_chunks` accumulation — args generally arrive across
many continuation chunks, not on the first chunk where the tool
name lands.  Follow-up work: stitch `tool_call_chunks` per
tool_call_id, emit `<name>: <args>` when complete (or stream args
character-by-character — see below).

Other dimensions worth iterating once the basic args preview lands:
- *Tool-result visibility.*  Right now elisp results stay inside the
  langgraph trace; the user sees only the agent's prose summary
  afterwards.  For a device the agent is MODIFYING this may be too
  opaque — a `status: eval_elisp result: <preview>` event would let
  the user spot a wrong-direction call early.  Trade-off: noisier
  on multi-call sessions; might warrant a "verbose" toggle.
- *Streaming partial args.*  Show args character-by-character as
  they stream in (like the bot text already does).  Costs an event
  per chunk per arg; consider only for slow tool-args generation.

** TODO Flexible config change management (revert any past change via chat)

Design scoped 2026-06-07:
[[file:docs/2026-06-07-flexible-config-revert.org][docs/2026-06-07-flexible-config-revert.org]]
(two tools =get_config_history= + single-ref =revert_config=; staged-revert
trio on =ConfigRepo=; apply-then-commit; reuse the =applied= event; behavior
eval in emacsos).

The next experiment *immediately after* conversation history — we go
straight here, deliberately skipping any intermediate "N-level only"
chat-revert step.

Today config undo is strictly one-level: the phone ROLLBACK button calls
=config_repo.rollback()= → =git revert --no-edit HEAD=, undoing only the
most recent =apply_config=.  *That one-level button stays as-is* — it's
the quick "undo the thing I just did" fast path, and it's all the button
needs to be.

The full system is conversational and *targeted*: "revert the change
about X, where X is any past apply" — e.g. "undo the cursor color change
but keep the font change", or "revert the last two things".  Driven from
*chat* (it needs the conversation context that conversation history
unlocks), the agent:
- surfaces the apply history to itself — each =apply_config= already
  commits with its SUMMARY as the git message, so =git log= IS the
  change list; no new persistence needed;
- maps a natural-language reference ("the cursor change") to a commit;
- reverts just that commit (=git revert --no-edit <sha>=), or a chosen
  set/range, history-preserving so roll-forward stays possible;
- handles conflicts honestly (=git revert --abort= + a "can't cleanly
  revert that — a later change touched the same thing" result) when a
  targeted/range revert doesn't invert cleanly.

So this single item subsumes what was once "chat-revert" + "N-level" +
"targeted": the one-level phone button is the fast path; this is the
rich, conversational path, and it's where we head next.

*** DONE Agent can't read current config after =/clear= (prerequisite)

Shipped: the =get_config= tool (=channel.py=) reads the committed config body
straight from the git repo, so the agent no longer relies on conversation
memory — =/clear= is safe AND there's no stale-setting resurrection.  Unblocks
the flexible-config revert above.

Surfaced 2026-05-23 by a live "set the cursor blue" turn right after a
=/clear= ("New chat").  =apply_config= replaces the whole config file, so
the config-apply skill tells the agent to *read the current config first*
and restate it.  But with conversation memory wiped by =/clear=, the agent
has no way to *find* the config: it tried =(user-init-file)=,
=(load-file)=, =(getenv "EMACS_CONFIG")= — none reach
=~/.emacs.d/emacsos/agent.el= (a server-side path it can't know) — and
LoopDetection then caught the distinct-args thrash and terminated the
turn.  Nothing was applied (the failure was *safe*), but the user's most
likely action after a reset — "now change X" — currently can't persist.

Root cause: the agent relies on conversation *memory* as the source of
truth for current config.  That memory is double-edged — with it the
agent can restate config (but resurrects stale settings, e.g. the
line-numbers bug that =/clear= was meant to cure); without it
(post-=/clear=) it can't apply at all.

Fix direction: stop relying on memory — give the agent a reliable read
path (a =get_config= / =read_config= tool, or inject the current
=agent.el= body into the skill/system context).  Then =/clear= is safe
(memory gone, config still readable) AND there's no resurrection (the
committed file is the source of truth, not memory).  A prerequisite for
the flexible config management above — that work also needs the agent to
navigate config state, so fold it in or land it first.

** DONE Sub-agent turns wedge the server (langgraph 1.2 streamed-path bugs)

Any /chat turn that spawned a SUB-AGENT (=task= → =research-agent=,
=context-agent=) wedged the moment the sub-agent ran: no next model call,
no error, just silence; then the orphaned worker wedged EVERY later turn
until the uvicorn worker was restarted.

*Real root cause* — a py-spy dump (2026-05-25) DISPROVED the original
shared-=SqliteSaver=-contention theory (kept at the bottom for the record).
Three distinct bugs, all from the langgraph 1.2.0 upgrade, layered:

1. *Deadlock.*  langgraph 1.2 defaults =durability="async"=, which submits
   every checkpoint =put= to a =BackgroundExecutor= chained via futures
   (=pregel/_loop.py:_checkpointer_put_after_previous=).  Under deep
   streamed sub-agent nesting the thread pool exhausts and the puts
   deadlock waiting on each other — backend-independent (NOT the sqlite
   connection).  The dump showed ThreadPoolExecutor workers all parked in
   =_checkpointer_put_after_previous=.  Fixed by passing =durability="sync"=
   to =agent.stream()= in =assist.Thread.stream_message=.

2. *Bug A — Overwrite parsing.*  Once turns completed, a node overwriting
   the =messages= channel delivered a =langgraph.types.Overwrite= wrapper
   (not a list); =stream.py:_tool_messages= crashed with =TypeError:
   'Overwrite' object is not iterable=.  Fixed via the shared
   =assist.stream_chunks.unwrap_messages=.

3. *Bug B — cross-thread generator.*  =_stream_turn= advanced the
   thread-affine stream generator (it holds =THREAD_QUEUE.acquire='s
   Condition + a ContextVar) across the default thread pool and closed it
   on the event-loop thread → the lock was released by a non-owning thread
   → =RuntimeError: cannot release un-acquired lock= → worker crash.  Fixed
   by pinning build/next/close to a dedicated =max_workers=1= pump so the
   whole generator lifecycle stays on one thread + context (mirrors the
   assist CLI, immune because it drives the generator on one thread).

*Resolution.*  assist branch =fix-streamed-subagent-deadlock= (durability +
=unwrap_messages= + CLI fix); emacsos branch =fix-streamed-chat-langgraph-1.2=
(=stream.py= routing + the single-thread pump).  Verified e2e 2026-05-25:
research turn completes start→end, sub-agent turn runs without crashing,
=_STREAM_LOCK= releases between turns, web blocking path unaffected.

*Original (WRONG) theory, kept for the record:* blamed =5f0dd90= "Persist
conversation history" for adding a process-wide =SqliteSaver= that
sub-agents supposedly contended on via a shared sqlite cursor.  The py-spy
dump showed the stall is langgraph's checkpoint-put pool, not the
connection — isolating the sub-agent checkpointer (the
=isolate-subagent-checkpointer= branch) did NOT fix it, confirming the
theory was wrong.  Client disconnect was likewise a red herring.

** DONE Remote connectivity: WireGuard for the away phone

*Shipped 2026-05-31* —
[[file:docs/2026-05-31-wireguard-away-phone.org][docs/2026-05-31-wireguard-away-phone.org]].
Two-peer topology (home dev box ↔ phone, no relay box — the home server is
already publicly reachable).  Phone wg conf uses the dev box's stable EUI-64
IPv6 as Endpoint so the same line works over wifi and over T-Mobile cellular
(which is IPv6-only).  =MTU = 1280= on the phone wg interface to survive
cellular PMTU + wg overhead for TCP.  Server-side firewall: IPv4 port-forward +
IPv6 inbound pinhole for UDP 51821.  Reproducible setup via
=deploy/wireguard/{server-add-peer,phone-bringup}.sh= + =make wg-add-peer= /
=make wg-phone-bringup=; private keys are generated on the phone and never
leave it.  Notes the sharp edges captured in the doc (wg-quick bounce required
when endpoint family changes; LAN ssh to phone is broken by the AllowedIP
trade-off — use =ssh phone-wg= → =10.0.0.X=; rfkill-persists-across-reboots
trap for cellular cutover, addressed in the playground scripts).

The original write-up below is preserved for historical context.

Today the whole channel assumes the phone and server share a LAN.
The phone POSTs =/chat= to the server's local IP, and the server
reaches *back* to the phone's emacs daemon via =emacsclient=
(=phone.call_emacs=), targeting whatever address the HTTP request
came from (=request.client.host=).  That return path only works
because both are on the same network.

The real deployment: *server stays home, phone goes out into the
world.*  When the phone is remote it connects home over WireGuard.
Two problems to solve:

1. *Server must be a WireGuard peer the phone can be reached at.*
   The back-channel (=eval_elisp= → =call_emacs= → phone) needs the
   server to *initiate* a connection to the phone.  That means a wg
   topology where the server can route to the phone's tunnel IP
   (phone as a peer with appropriate =AllowedIPs=; server side
   configured to reach it).  Without this, the agent can receive a
   request from the away phone but can't act on it.

2. *Home-vs-away detection → pick the route.*  When home, reach the
   phone at its LAN IP (lower latency, no tunnel); when away, reach
   it at its wg IP.  The existing =request.client.host= substitution
   in =phone.py= may already do most of this for free: if the phone
   always POSTs from the interface it's reachable on (LAN IP at
   home, wg IP away), then the source address of the request IS the
   correct return address.  Worth validating that assumption against
   the actual wg routing before building anything fancier — we may
   not need explicit home/away state at all, just correct wg config
   + the address-from-request trick we already have.

Open questions for the future design doc:
- Does the phone's outbound =/chat= reliably egress on the same
  interface the server should return on?  (Determines whether
  =request.client.host= is sufficient or we need explicit detection.)
- wg keepalive / NAT-traversal so the server-initiated back-channel
  survives the phone being behind cellular CGNAT.
- Latency budget: =call_emacs= has a 15s timeout (=EVAL_TIMEOUT_
  SECONDS=); a wg round trip over cellular may need a higher cap for
  the away case.
- Auth-file host field: =parse_auth_file= already discards the
  posted host and substitutes =request.client.host=, so the phone
  doesn't need to know its own reachable address — good, that part
  already generalises to wg.

* Usability

These add EmacsOS's first device-side system-integration layer: today =os.el= is

** TODO Audio I/O ("headphone jack")

*UPDATE (2026-06-18)* — see [[file:docs/2026-06-18-call-audio.org][docs/2026-06-18-call-audio.org]].
The modem HAT is the Waveshare *4G HAT (B)*: it already has an onboard NAU8810
codec + a 3.5mm TRRS headset jack (call audio via =AT+CSDVC=, the analog
fallback) *and* exposes call audio as a raw PCM stream on =/dev/ttyUSB4=
(=AT+CPCMREG=1=) — the software path, which records/transcribes today.  For
*media* audio (TTS/STT, not the call): a USB audio dongle (Sabrent AU-MMSA) into
a free USB-A port on the HAT's built-in hub — no extra OTG hub needed.  Two
inherently-separate endpoints; unifying onto one headset is the Option-1 bridge.

The Zero W has *no analog audio* — no 3.5mm jack and no analog out on the header
(unlike full-size Pis) — so this is really "add audio I/O", output *and* a mic (calls
and STT both need capture).  Options: an I2S DAC/codec HAT (e.g. MAX98357A out + an
I2S or USB mic, or a combined codec like the WM8960), a USB audio dongle (needs an OTG
hub — there's one micro-USB data port), or PWM-on-GPIO out (poor, and output-only —
not enough for calls).  The hard part is *call-audio routing*: the modem's voice path
has to reach speaker + mic — either the modem exposes digital audio (USB/PCM) ALSA can
route, or its analog codec pins must be wired to the audio device.  Resolve this
jointly with the modem choice.  Done when ALSA can play and record on-device and
in-call audio works end to end.

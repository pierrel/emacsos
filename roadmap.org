#+title: EmacsOS Roadmap
#+date: 2026-05-17

Each experiment is its own design doc + branch (see =docs/= for
landed ones).  This file collects forward-looking work that
doesn't fit any specific experiment yet — usability iteration,
cross-cutting concerns, follow-ups discovered live on the phone.

* Ergonomics iteration

Live testing of PR #6 (assist-import) surfaced several rough edges
in the phone UX that aren't load-bearing for any specific
experiment but compound across all of them.  Worth a dedicated
pass.

** TODO Dynamic keyboard surface based on top buffer

Currently the keyboard surface (bottom window) shows whichever
page was last selected — KBD / CMD / MODE / CHAT.  Switching
context across the top buffer doesn't auto-show the appropriate
controls.  When the user is in =*chat*= they almost always want
SEND/CLEAR visible without manually tapping CHAT; when they're
editing an org file they usually want T9 keys, etc.

Direction: derive the bottom-surface page from the top buffer's
major mode (or buffer name).  =*chat*= → CHAT page; org-mode →
something org-aware; everything else → KBD.  Keep a manual
override for the moments the auto-selection is wrong.

** TODO Tab button on the keyboard

T9 keyboard has SPC, RET, DEL, CAPS but no TAB.  Tab is load-
bearing in lots of contexts (completion, structured editing,
field navigation).  Add as a utility button alongside the others.

Decide: replace one of the existing util slots, or grow the row?
Spacing budget on a 320x240 screen is tight.

** TODO Keyboard layout + sizing iterations

The Optimal-T9 layout from the Qin et al. paper is the v1
baseline.  Live use will surface things the paper doesn't capture
on this specific screen (gap proportions, scale factor between
letter and util buttons, fingertip-vs-stylus accuracy bias,
number row treatment, punctuation strategy).  Iterate based on
what's actually painful in real use rather than redesigning
preemptively.

** TODO Font choice + sizing

The default emacs face on the phone is whatever the system X
fontconfig defaults pick — not optimized for a 320x240 surface
held at arm's length.  Pick a font (and sizes for transcript /
input / keyboard / status) that reads well at this density:
legibility at small px counts, distinguishable lowercase l vs.
uppercase I vs. digit 1, comfortable line-height in =*chat*=.
Candidates: a programming font (Iosevka, JetBrains Mono) tuned
for clarity at small sizes, or a screen-optimized humanist like
Inter.  Try a couple, decide on the phone, codify in =os.el=
(or a per-face block in the init snippet) so phone-install
sets it consistently.

* Tool-call transparency

The emacs-modifying channel ships with `status: calling <tool_name>`
events for each new tool invocation.  Intended UX was richer
(`status: <tool_name>: <truncated args>`) but the implementation
needs `tool_call_chunks` accumulation — args generally arrive across
many continuation chunks, not on the first chunk where the tool
name lands.  Follow-up work: stitch `tool_call_chunks` per
tool_call_id, emit `<name>: <args>` when complete (or stream args
character-by-character — see below).

Other dimensions worth iterating once the basic args preview lands:
- *Tool-result visibility.*  Right now elisp results stay inside the
  langgraph trace; the user sees only the agent's prose summary
  afterwards.  For a device the agent is MODIFYING this may be too
  opaque — a `status: eval_elisp result: <preview>` event would let
  the user spot a wrong-direction call early.  Trade-off: noisier
  on multi-call sessions; might warrant a "verbose" toggle.
- *Streaming partial args.*  Show args character-by-character as
  they stream in (like the bot text already does).  Costs an event
  per chunk per arg; consider only for slow tool-args generation.

* Other / cross-cutting

** TODO Phone tempdir leak

`emacsos-server` now constructs a fresh `tempfile.mkdtemp(prefix=
"emacsos-thread-")` per /chat (channel PR dropped the Thread
singleton).  Was once-per-server-rebuild before; now once-per-
turn.  Over a day of moderate use, `/tmp/emacsos-thread-*` will
accumulate hundreds of directories.  systemd's PrivateTmp or
tmpwatch will eventually deal with it, but cleanup on stream end
(or short TTL) is cleaner.

** TODO call_emacs return tuple → typed kind

`channel.eval_elisp`'s `is_unreachable` classifier reverse-engineers
`phone.call_emacs`'s error-string shapes (`emacsclient:` prefix,
`exit N`, `[Errno N]`, `timed out`, `auth file:`, `binary not
found`).  Brittle: changing the wording in `phone.py` silently
breaks the no-retry hint.  Lift the classification into
`call_emacs`'s return shape (eg. `CallResult(kind: Literal["ok",
"unreachable", "elisp_error"], output: str)`) and switch in the
tool.  Deletes ~12 lines of substring matching + the dedicated
unreachable-shape tests.

** TODO Redact secrets in `/chat` request log

`app.py`'s `log.info("POST /chat msg=%r", req.message)` logs the
user's chat input verbatim.  `channel._redact` exists and could be
applied here.  Surfaced by the code-review team; not done in the
channel PR because that PR shouldn't widen scope to `app.py`'s
logging.

** TODO Remote connectivity: WireGuard for the away phone

Today the whole channel assumes the phone and server share a LAN.
The phone POSTs =/chat= to the server's local IP, and the server
reaches *back* to the phone's emacs daemon via =emacsclient=
(=phone.call_emacs=), targeting whatever address the HTTP request
came from (=request.client.host=).  That return path only works
because both are on the same network.

The real deployment: *server stays home, phone goes out into the
world.*  When the phone is remote it connects home over WireGuard.
Two problems to solve:

1. *Server must be a WireGuard peer the phone can be reached at.*
   The back-channel (=eval_elisp= → =call_emacs= → phone) needs the
   server to *initiate* a connection to the phone.  That means a wg
   topology where the server can route to the phone's tunnel IP
   (phone as a peer with appropriate =AllowedIPs=; server side
   configured to reach it).  Without this, the agent can receive a
   request from the away phone but can't act on it.

2. *Home-vs-away detection → pick the route.*  When home, reach the
   phone at its LAN IP (lower latency, no tunnel); when away, reach
   it at its wg IP.  The existing =request.client.host= substitution
   in =phone.py= may already do most of this for free: if the phone
   always POSTs from the interface it's reachable on (LAN IP at
   home, wg IP away), then the source address of the request IS the
   correct return address.  Worth validating that assumption against
   the actual wg routing before building anything fancier — we may
   not need explicit home/away state at all, just correct wg config
   + the address-from-request trick we already have.

Open questions for the future design doc:
- Does the phone's outbound =/chat= reliably egress on the same
  interface the server should return on?  (Determines whether
  =request.client.host= is sufficient or we need explicit detection.)
- wg keepalive / NAT-traversal so the server-initiated back-channel
  survives the phone being behind cellular CGNAT.
- Latency budget: =call_emacs= has a 15s timeout (=EVAL_TIMEOUT_
  SECONDS=); a wg round trip over cellular may need a higher cap for
  the away case.
- Auth-file host field: =parse_auth_file= already discards the
  posted host and substitutes =request.client.host=, so the phone
  doesn't need to know its own reachable address — good, that part
  already generalises to wg.

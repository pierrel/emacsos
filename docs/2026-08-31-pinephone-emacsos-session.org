** 2026-09-02 hands-on power result and automatic-idle design

Battery measurement remains mixed.  Active use initially drew roughly
0.8--1.0 A with Firefox open and capacity fell from 93 to 80 percent in about
15 minutes, although part of that step may be gauge settling after unplug.
After Firefox closed, observed awake draw ranged roughly 0.37--0.75 A.  Once

daily-driver battery claim; a matched duration run remains necessary.

The power policy uses Alpine's 66 KiB =swayidle= 1.8.0 package, which is linked
against the image's existing elogind.  Physical input while active resets both
idle deadlines.  At 60 seconds =session-power idle-blank= records a
blank transition, disables the Goodix touch device, and powers down DSI-1.  At
180 seconds =session-power suspend= acts only from =blank= and retains its
private state lock.  Its exact doas command then enters the root-owned
=emacsos-openrc-suspend= helper.  That helper
requires selected =deep= sleep and kernel filesystem syncing, performs the
=/sys/power/wakeup_count= handshake, and writes =mem= to =/sys/power/state=.
A successful state write returns only after the kernel has resumed, so a
power-key handler cannot overtake an asynchronous suspend request.  A short
physical power press is the sole normal wake owner: =active= becomes =blank=; =blank=
becomes =active= with DSI and touch restored.  A handler
started by the wake press waits for the state lock and restores the devices
after the kernel call returns.  There is deliberately no swayidle =resume= or
=after-resume= display callback.  Such a callback can race the same power-key
event and blank the just-woken screen.

The locked graphical account is not an elogind login session.  Its direct
=loginctl suspend= failed, while root elogind requests were asynchronous and
could report acceptance before the kernel began suspending.  The installed
doas rule therefore grants that account only the exact, zero-argument
=/usr/local/sbin/emacsos-openrc-suspend= command.  It grants no shell,
arbitrary argument, RTC, shutdown, or general file authority.
The state helper pins its command path, home, runtime, and Sway socket instead
of trusting those caller variables; accepts one fixed action enum; and
discovers one owner-checked socket only inside the private runtime directory.
Non-press lock attempts and every Sway operation are bounded, while the
asynchronous power-key handler waits for an in-flight kernel transition.  The
helper records transitional states before device changes and restores an
active panel after an interrupted or malformed state.  The suspend and display
state locks remain owned through the complete kernel transition.  =swayidle=
and its command descendants run in an owned
process group; session teardown does not return until that group is empty, so
the supervisor cannot overlap an old suspend worker with a replacement
session.  Session startup fails unless the start action proves it is already
inside the exact v25 service cgroup with working kill and event interfaces.
For explicit service stop, the OpenRC stop process first moves itself to the
parent cgroup, then writes the exact service-cgroup =cgroup.kill= interface and
verifies =populated 0= before removing the private runtime.  It does not rely
on this OpenRC release's broken generic cgroup path lookup or kill the stop
action along with the service.

The 60/180-second policy intentionally provides no screen lock yet.  This
remains a non-personal synthetic lab.  The explicit =wake= action is currently
for session startup and controlled recovery only; a future non-input modem-wake
path must also define how it rearms the idle timer.  Promotion still requires a
real touch-operable lock, repeated automatic blank/suspend/physical-wake runs,
duration and battery results, and modem wake/registration/call/SMS checks.

* Evidence and hypotheses

The phone is an original 3 GiB PinePhone reporting hardware revision 1.2.  On
2026-08-31 it ran postmarketOS edge, Linux 6.18.3, Phosh/Phoc 0.57, and had
Binder, memfd, PSI, and DRM render support.  Its repositories offered Sway,
Cage, PGTK Emacs, Firefox, mobile-config-firefox, and Waydroid.

The latest failed power-button cycle did not enter suspend.  The journal
recorded a short power-key press at 16:16:48 and Phoc turning DSI-1 off at
16:16:50.  Linux continued running and reconnected Wi-Fi through 16:19, but no
second power-key event or DSI modeset was recorded before the forced restart.
Earlier successful cycles recorded both.  The AXP803 power-key wake source was
enabled.  This leaves two hypotheses:

Two later stock-session boots on 2026-08-31 froze within minutes while USB
power was online, before any EmacsOS payload was installed.  SSH and both known
LAN paths disappeared.  The preceding journal again contained no suspend,
resume, GPU fault, kernel fault, or OOM.  It did show repeated Phrog/Phoc layout
transaction failures, a greeter-side OSK restart loop, and a greetd user slice
peaking at about 624 MiB before Phosh became ready.  The journal then ended at
the forced restart.  This is evidence against the new session causing the
freeze and further motivates isolating the stock graphical stack before
changing the postmarketOS kernel or device base.

- H1: Phosh/Phoc or its input/display path loses the wake.  Sway survives the
  same display-off and deep-suspend workload.
- H0: the kernel, AXP803, or board loses the wake or physical key event.  Sway
  reproduces it, and further PinePhone UI work stops.

RTC wake separates generic deep suspend from the physical button.  Successful
RTC resume with failed physical wake points at the PMIC/input path.  Failed RTC
resume points below the shell at the kernel, firmware, or hardware.

** Base-image and upstream evidence

The observed modem failure has an exact upstream analogue in pmaports issue
#4265: postmarketOS v25.12 PinePhones lost the EG25 USB connection every five
to fifteen minutes, followed by enumeration failures, QMI and =qmi_wwan=
timeouts, and recovery only after reboot.  Its reporter said v25.06 worked.
The issue was closed because v25.12 reached end of life, not because a fix was
identified.  A downloaded v25.12 image therefore remains a regression
reference and is not a fallback candidate.

The supported v26.06 release and the installed edge image both use the
=6.18.3= PinePhone kernel, so changing between them is not a meaningful kernel
A/B.  The v25.06 branch uses =6.13.8= and is the smallest controlled diagnostic
change.  It is end-of-life software, not a daily-driver destination.  The
prepared fallback is therefore a locally built v25.06 OpenRC console image,
with only Pierre's SSH public key provisioned, for a different known-good SD
card.  Tests add one layer at a time: console and Wi-Fi with both modem daemons
disabled; =eg25-manager= alone; =ModemManager= and mobile data; then graphics.
Failure before the modem or graphics on a different card would strongly favor
battery, board, or hardware.  Stability would justify a supported v26.06
userspace with a deliberately tested older/backported kernel rather than
remaining on v25.06.

The supported v26.06 OpenRC recovery-v2 image is now the first test because a
passing supported base can become the actual installation without another
comparison.  If it fails, the v25.06 image on the same card creates the
controlled 6.18-versus-6.13 boundary that the stock Phosh image could not.  A
separately verified DanctNIX barebone image with 6.15.6 remains only the third,
cross-distribution reserve.

The original PinePhone was moved from postmarketOS community to testing on
2026-08-05 because its =6.18.3= kernel exceeded the project's six-month
freshness requirement.  Upstream also records why it was not simply advanced:
newer kernels can break incoming calls across suspend by restarting the modem

postmarketOS shell would avoid the low-level problem.

** Historical session responsibilities

In v0, Sway owns input bindings and =session-power= owns only same-user DSI-1
DPMS commands.  A DPMS command failure requests Sway exit.
=emacs-supervisor= waits for the static Emacs probe and its private IPC server
to map, reports service readiness, and binds Emacs and Sway liveness together.
A lifetime systemd restart limit bounds whole-stack recovery.  A
session-lifetime logind inhibitor blocks only
competing =handle-power-key= handling; it does not inhibit sleep.

The promotable path adds a narrow same-user coordinator.  It starts the locker,
waits for its protocol-ready signal, monitors it, sequences DPMS, arms an RTC
through a fixed helper when testing, and requests normal logind/systemd
suspend.  The locker alone owns PAM authentication.  Emacs and the harness own
none of this state.

A short power press acquires the lock and turns the panel off immediately.  If
the phone remains idle for 120 seconds, the coordinator requests deep suspend.
The ordinary idle path begins the same sequence after a configurable five
minutes without input.  A press while merely blank
turns the panel on to the lock; a press after deep suspend first wakes the
hardware and then shows that same lock.  Successful unlock returns to the exact
foreground application.  A locker failure before protocol acquisition aborts
suspend and restores the unlocked panel.  A failure after acquisition never
reveals the authenticated session: the coordinator ends Sway so the display
manager starts a fresh locked Phosh login, or reboots to stock if that fallback
cannot be proven.  Tests force failure on both sides of readiness with Firefox
and Waydroid in front.  No script enters or captures a real PIN.  The global
Phosh and logind policies remain unchanged.

The selected =/sys/power/mem_sleep= state must be =deep=.  Every accepted test
requires a kernel suspend-entry and resume pair.  A secure, touch-operable
Wayland session lock is a promotion gate.  An Emacs PIN buffer is not a security
boundary and cannot substitute for it.

The implemented v0 home is a static non-personal PGTK Emacs frame.  It contains
no launcher, Firefox button, keyboard, Waybar, or full EmacsOS configuration.
Its only purpose is to prove native PGTK rendering and supervised recovery.

The planned feasibility home adds large fixed buttons for Firefox, keyboard,
close-app, and Home.  A two-button unlocked navigation strip
rendered by packaged Waybar and reserved by Sway remains touch-reachable while
an application is maximized:
Home focuses Emacs and Keyboard toggles the same-user Wayland keyboard.  It is
covered by the secure lock surface.  The session also retains fixed hardware
bindings for Home and keyboard recovery if Emacs or the navigation strip dies.
The first Emacs or keyboard failure gets one bounded restart from its fixed
known-good file set; the hardware binding invokes that same recovery.  A second
failure ends Sway and reaches a fresh locked Phosh login.
The harness automates Home → Firefox → keyboard show/type/hide → Home → Firefox
close → Home and screenshots every visible transition.  This minimal launcher
ships before physical acceptance; only its polished Assist home is deferred.
Waybar owns only these two buttons, Sway owns focus and hardware bindings, and
the fixed =toggle-osk= command owns keyboard state.  Neither Emacs nor the bar
supervises another component, and this is not a general panel framework.

The planned general keyboard serves Emacs, Firefox, and Waydroid.  The locker provides
an integrated touch keypad within its single secure lock surface;
synthetic input does not substitute for either path.  The home intentionally
does not load =network.el= or the current =phone-call.el=: the former polls =mmcli= while
awake, and the latter owns SIM7600-specific raw-AT behavior that is not valid for
the PinePhone EG25-G.  Calls, Chatty, feedbackd, and notification integration
are deferred until power and recovery pass.  Gate-zero records the current
system modem, network, audio, and WireGuard state; the real-session gate later
requires each service to remain healthy.
Their real commands and app IDs come from live inventory rather than
assumptions.

** Historical security and privilege boundaries

The installation orchestrator accepts no paths, package names, session names,
or commands from arguments or the environment.  Pierre's one authenticated
bootstrap command first copies =bootstrap-root= without following symlinks into
a private root directory, verifies its reviewed checksum there, and executes
only that immutable copy.  The bootstrap applies the same snapshot-and-hash
rule to the admin helper.  The manually authorized install
runs as a bounded root transient service so an SSH or terminal loss cannot
interrupt the package transaction.

The admin helper copies the fixed payload into a private root snapshot before
verification or package work, with a one-MiB file-size limit, and installs only
from that snapshot.  The package simulation output has the same one-MiB cap.
The APK files are downloaded once through APK's signed-index/package validation;
both simulation and installation then use that same root-owned snapshot with
network access disabled.
The
complete release directory is constructed privately and renamed into place
before the disabled system unit and PAM policy are installed.  Every existing destination is
preflighted for its intended root-owned type.  Installation never recursively
copies or changes ownership of a user tree.  Packages come only from the
phone's configured signed postmarketOS/Alpine repositories; the installer
performs the identical simulated transaction first and verifies the stock
Phosh executable before and after the real transaction.

The reviewed manifest digest is embedded independently in the verified admin
helper.  The admin allowlists exactly nine staged regular files, rejects extra
entries, snapshots them without following symlinks under per-file and total
bounds, verifies the pinned manifest and every payload digest, and installs
only from that root-owned snapshot.  No staged code runs before this trust chain
is complete.

At Pierre's explicit request, the operator currently has temporary unrestricted
passwordless sudo in =/etc/sudoers.d/99-user-nopasswd= so unattended live
development can proceed through freezes and reconnects.  This is broader than
the payload requires: compromise of the operator account or its SSH key is
currently root compromise.  Remove that rule or replace it with the fixed
helper-only commands before promotion.  Independently of that temporary host
policy, the fixed root helper accepts only =install=, =activate=, or =cleanup=,
requires =SUDO_USER=user=, and serializes them with one root-owned lock.  Install
does not enable or start the service.
Activation verifies the committed release, enables the direct unit, disables
and stops greetd, releases and activates tty1, and waits boundedly for an
owner-checked readiness marker written only after Emacs maps.
Once activation begins changing unit state, failure disables both graphical
boot units and stops the lab so neither an
unvalidated lab nor the unstable stock shell can start on the next boot; SSH is
the documented v0 repair path.  A preflight verification failure changes no
unit state.  Cleanup tolerates partial installation state, terminates the
explicit lab process set, restores and verifies greetd on active seat0/tty7
first, and only then removes the unit, PAM policy, release, dedicated account, private lab home, and
admin helper.  The unprivileged staging cache is retained for a subsequent
reinstall and can be removed by the operator.  If greetd cannot be restored,
recovery artifacts are retained.
APK packages remain installed.

The unlocked compositor never runs as the SSH/operator user.  Its dedicated
locked-password account has an empty mode-0700 home, no SSH or administrative
membership, no access to the operator home, no inherited user services or
agents or user manager, and only the video/input access required by fixed
hardware groups.  Its polkit rule grants only the exact logind power-key inhibitor
used by the service and denies power-off, networking, modem, persistence, and
all other brokered authority.
The v0 service makes the host filesystem read-only apart from its private
runtime/home and private temporary directories, and drops capabilities and new
privileges.  It deliberately has no systemd device or address-family filter:
both compile BPF programs whose retirement is unsafe on this kernel.
This is synthetic lab isolation, not a lock screen.

There is currently no privileged RTC or suspend helper.  That fixed enumerated
boundary is added only when the planned suspend harness exists.  The payload
adds no arbitrary =systemctl= or =rtcwake= command, setuid helper, root input
daemon, browser remote-debug listener, or new network service.  The operator's
temporary general passwordless sudo is an external development exception, not
a payload interface, and must not survive promotion.  Raw
screenshots and transcripts remain confidential and untracked.  SSH recovery
is key-authenticated; the current stock server also advertises password and
keyboard-interactive methods, an existing hardening item outside this graphical
cutover.  Session work does not rewrite SSH configuration.  The
non-secure lab service has bounded startup and restart attempts.  It never
starts greetd implicitly; authenticated cleanup is the only stock transition.

Waydroid shares the host kernel and is not a strong sandbox.  It uses a fresh
test image from one fixed official image channel whose published archive
digests were verified before extraction.  It has no ADB TCP or debug mode, no
autostart, and no host or media directory containing personal state.  The
current package-provided nftables policy permits Android traffic to the host and
ordinary forwarded destinations; it is sufficient for the built-in-app
feasibility smoke but not for an untrusted third-party APK.  No third-party app
or Android account is admitted until a fixed, verified policy denies host,
WireGuard, LAN, link-local, loopback, carrier-grade NAT, multicast, and other
private destinations while retaining only DHCP/DNS and ordinary Internet
egress, and the native browser and Waydroid session no longer share authority
to the root container manager.  NAT traffic and the new per-UID D-Bus rule alone
do not satisfy those future boundaries.

Firefox uses its normal sandbox and a fresh non-symlink test profile directory
created by the graphical user with mode =0700= and private files.  The profile
is removed after the lab gate.  Fixed URL, title, and app-ID values are passed
as argv and never interpolated into shell or Sway command strings.  Input
automation runs as the graphical user, uses
fixed inert strings, verifies the intended app and focus before typing, and
does not use =uinput=, =ydotool=, or a root device.  The Emacs server is a Unix
socket in the private runtime directory, never TCP.  Hot-reloaded elisp remains
same-user code and cannot modify or invoke arbitrary privileged operations.

** Historical promotion and stop conditions

After every automated and physical gate passes, replace the disposable direct
lab account with the locked daily-driver EmacsOS session.  Keep Phosh installed
and retain boot-time automatic last-known-good
fallback that works without networking, plus one fixed interactive recovery
command.  Every fallback terminates the old graphical login and reaches a fresh
locked Phosh greeter; it never directly starts Phosh inside an authenticated
Sway session.  SSH is useful evidence and recovery access but is not the only
recovery mechanism.

Software defects in locking, keyboard input, recovery, or telephony block
promotion and are diagnosed rather than mislabeled as hardware failure.  Stop
the PinePhone port only when evidence localizes a deep-suspend, RTC-resume,
physical-wake, or carrier-wake failure below the graphical session, or when the
matched absolute power budget cannot meet the recorded daily-driver threshold.
Do not compensate by disabling suspend.  At that point the honest next step is
different hardware or focused kernel/firmware work, not more interface code.

Promotion replaces the plain feasibility launcher with the real PinePhone
Assist home.  It reuses the existing deterministic Emacs commands and adds
fixed commands to launch/focus/stop Calls, Chatty, and Waydroid without a second
component registry.  A PinePhone-specific Make target reuses the existing
SSH/scp + remote-emacsclient deployment pattern, names a local Unix Emacs server
socket under the private runtime directory, and deploys only the PinePhone file
set.  It does not use the current TCP server path or route hot reload through
the acceptance harness.

* Superseded v26.06/systemd implementation and verification record

** Historical control flow

The superseded v26.06 path was deliberately smaller than a phone shell.  An
unprivileged host script stages a checksum-pinned nine-file payload.  Pierre
then authenticates two fixed root commands: the first installs the independently
hashed admin helper; the second snapshots and verifies the staged files,
downloads one signed recursive APK set, simulates and installs those exact APK
files offline, creates the locked graphical account, and installs the direct
unit disabled.  Nothing changes the active graphical session during install.

The headless harness runs that installed release with wlroots' headless/pixman
backend.  It requires the private Emacs IPC server and mapped PGTK client,
injects pointer and F12 input, captures the resulting screenshot, kills Emacs,
and requires the supervisor and Sway to terminate within a bounded interval.
Only after that pass does the Make target print the separately authenticated
activation command.  Activation verifies the installed release again, then
switches tty1 from greetd to the dedicated direct service.  Explicit cleanup
restores and proves active greetd on seat0/tty7 before removing root-managed lab
state.

At runtime, systemd creates a minimal noninteractive PAM/logind session for the locked
=emacsos-lab= account.  The direct launcher requires active seat0/VT1, starts
Sway, and hands both Sway and PGTK Emacs to one supervisor.  The supervisor
checks the display output, mapped Emacs client, and private IPC socket every ten
seconds.  A lost child or heartbeat fails the entire service; systemd permits
only two lifetime retries beyond the initial start.  Failure leaves a blank
display and authenticated SSH recovery rather than silently starting the
unstable Phosh stack.

** v26.06/systemd review findings and disposition

Four local review rounds covered correctness, process liveness, error paths,
adversarial security, simplicity, design adherence, and documentation drift.
The verified in-scope findings were fixed:

- *IMPORTANT:* clean child exit could leave a dead-looking compositor;
  supervision now treats every monitored child or heartbeat loss as failure.
- *IMPORTANT:* several startup, IPC, and cleanup paths could wait forever;
  startup, TERM-to-KILL teardown, SSH, systemd, package output, and smoke waits
  now have explicit bounds.
- *IMPORTANT:* a rolling restart interval did not enforce a lifetime failure
  cap; =StartLimitIntervalSec=infinity= now makes the initial start plus two
  retries the complete budget.
- *IMPORTANT:* the graphical PAM session could inherit a user manager and
  desktop authority; it now uses a light session, a locked dedicated account,
  a narrowly allowlisted inhibitor with deny-by-default polkit policy, and a
  fixed capability/filesystem boundary plus ordinary video/input group access.
- *IMPORTANT:* package resolution and installation could diverge; one signed
  root-owned recursive APK snapshot now feeds both offline simulation and
  offline installation.
- *IMPORTANT:* activation failure could leave an unvalidated lab enabled for
  the next boot; after unit-state mutation begins, the failure trap disables
  both graphical boot units and terminates the lab.  Preflight failure changes
  no unit state.
- *IMPORTANT:* documentation overstated inventory and cleanup behavior; it now
  distinguishes repository simulation from snapshot installation, partial-state
  cleanup from repeat invocation, retained user staging cache, and private
  temporary writes.
- *IMPORTANT:* deployment forced public-key authentication but trusted the SSH
  profile username; all inventory, staging, and headless operations now force
  the remote =user= account and disable password, keyboard-interactive, GSSAPI,
  and host-based authentication.
- *NIT:* signal handlers that cleaned up without exiting could continue a
  privileged or graphical operation; every new shell entry point now exits on
  HUP, INT, or TERM and performs its EXIT cleanup exactly once.
- *IMPORTANT, live:* Sway ignored the preassigned IPC socket name; both the
  direct launcher and headless harness now derive the socket from the actual
  Sway PID.
- *IMPORTANT, live:* pretty-printed multiline output JSON defeated line-local
  matching; output probes now flatten the JSON before applying their fixed
  checks.
- *IMPORTANT, live:* exporting =WAYLAND_DISPLAY= before the real compositor
  made wlroots choose a nested Wayland backend instead of DRM.  The direct
  launcher now unsets it before Sway and discovers the one socket Sway creates
  before launching Emacs.
- *IMPORTANT, live:* deny-all polkit also denied the intended power-key
  inhibitor and caused an authentication agent to appear.  The lab rule now
  permits only =org.freedesktop.login1.inhibit-handle-power-key= for the locked
  lab user, the service forbids interactive authorization, and all other
  actions remain denied.
- *NIT, live:* the broad PAM session started GNOME keyring and Emacs displayed
  its startup help until first input.  The final PAM stack is noninteractive
  plus =pam_systemd=, and an Emacs startup hook clears the echo area after
  command-line processing.
- *BLOCKER, live:* after repeated forced graphical recoveries, the kernel
  entered a permanent RCU stall in =bpf_prog_free_deferred= while executing
  =bpf_arch_text_invalidate=.  Modem QMI timed out, Wi-Fi and SSH became
  unreachable, and later power-key events were logged without a usable screen.
  Removing the explicit systemd =DevicePolicy=closed= eliminated its cgroup
  device BPF program, but a second forced-recovery run still became unreachable
  before the kernel's stall-reporting interval.  The remaining
  =RestrictAddressFamilies= directive also compiles a seccomp BPF filter, so it
  is removed as well.  The locked account now relies on ordinary video/input
  group DAC while its capability, filesystem, PAM, polkit, and account
  boundaries remain.  One clean reboot clears deferred kernel state before an
  instrumentation-free plugged/unplugged stability comparison.  The first half
  of that comparison then failed: after clean boot and activation, the phone
  remained healthy through the midpoint of a quiet ten-minute plugged-in idle
  interval but was unreachable over both WireGuard and LAN at the end.  USB
  power was online throughout, and the interval contained no graphical test or
  service transition that could retire a per-session BPF program.  This
  falsifies removal of those two BPF-producing unit directives as a sufficient
  fix.  A subsequent short physical power-button press produced no display
  response.  It does not yet distinguish a USB-C/board fault from a different
  kernel or graphical hang; the next evidence is whether unplugging restores
  input, the previous-boot journal, and the matched unplugged idle control.
  Unplugging the already-wedged phone and issuing another short power-button
  press did not restore it.  After forced reboot, the journal showed no
  suspend or fault report and ended after the midpoint SSH-created user manager
  shut down.  A matched unplugged run with one SSH session held open passed ten
  minutes, and the phone remained healthy for two minutes after that session
  shut down.  The phone later wedged before the 22-minute follow-up while USB-C
  remained unplugged.  This excludes USB-C presence as a necessary cause; it
  does not exclude delayed BPF retirement after SSH/user-manager teardown or a
  separate nondeterministic kernel hang.  Temporary systemd linger then kept
  the same operator user manager alive across all SSH sessions.  The unplugged
  phone passed a clean ten-minute checkpoint but lost WireGuard and LAN before
  the twenty-minute checkpoint.  User-manager teardown is therefore not a
  necessary cause either.

One proposed change was rejected: automatically starting Phosh after a v0
session crash conflicts with the explicit requirement that greetd and Phosh not
appear during this experiment, and would reintroduce the stack correlated with
the freezes.  Explicit authenticated cleanup is the only v0 transition back to
stock.  Automatic locked offline fallback remains mandatory before promotion.

Two focused correctness/liveness reviewers exceeded their five-minute
backstops while exploring platform documentation and produced no final finding;
they were terminated rather than allowed to block the loop.  Their partial
analysis was covered by the completed security, documentation, and focused
follow-up passes.  One reviewer-side Emacs invocation could not create a
temporary native-comp directory because that reviewer was intentionally
read-only; the same test passes in the normal local test environment.

- two new minimal PinePhone home ERT tests;
- eight OpenRC launcher ERT tests;
- both OpenRC installer and boot-selector transaction containers;
- shell syntax for every new entry point;
- manifest membership, every payload checksum, and the independently embedded
  manifest checksum;
- systemd unit validation;
- static assertions for account, PAM, restart, group-based device access, filesystem, socket,
  polkit, SSH-authentication, and offline-package boundaries;

Live verification passed the signed APK snapshot transaction, installed-release
hash check, cleanup to active stock greetd, repeated headless smoke, direct
seat0/VT1 and DRM activation, real DSI output and tree assertions, Emacs IPC,
synthetic pointer and keyboard input, real-display screenshots, eight simulated
power-key DPMS cycles across the last two payloads, and two intentional Emacs
failure recoveries.  On the final payload the direct service started with no
GNOME keyring or authentication agent; NetworkManager, ModemManager, SSH, and
the exact power-key inhibitor stayed active.  The graphical checks themselves
had only the expected forced-failure journal entry and nonfatal wlroots
seatd/realtime fallbacks, but the later previous-boot inspection found the
kernel-level BPF/RCU stall described above.

The first forced reboot proved direct boot and restored networking, but it was
not a clean software-requested reboot.  A later clean reboot proved the fully
BPF-filter-free service could install, pass headless smoke, activate, and remain
healthy for several plugged-in minutes; loss of both network paths by the
ten-minute check blocks further recovery stress until its previous-boot journal
is collected and the matched unplugged idle control is run.  Deep
suspend/resume, Pierre's physical touch acceptance, modem registration after
sleep, and authenticated stock recovery after the final payload remain
unproven.  Firefox and Waydroid now pass their plugged-in automated feasibility

acceptance.  The OpenRC session has also passed more than twenty DPMS cycles
across reviewed payloads without replacing its graphical processes.

** Hard parts and learnings

The hard part was not drawing an Emacs screen.  It was constructing a direct
graphical login that can fail without corrupting recovery, does not borrow
authority from the SSH user or a desktop user manager, and cannot turn a dropped
SSH connection into a half-installed package set.  The stock freezes also made
failure attribution central: a headless compositor test is useful evidence, but
only repeated real DSI/PMIC suspend cycles can separate Phosh failure from a
kernel or board defect.

The main learning is that “minimal” must describe ownership as well as process
count.  One compositor, one application, one supervisor, one fixed root helper,
and explicit promotion gates are easier to reason about than a stripped desktop
whose greeter, lock screen, policy broker, and user services still make hidden
decisions.

** Deferred findings and next actions

The fresh installer rolls back ordinary errors and caught signals, but an
uncatchable kill or power loss during root mutation can leave a partial install
that its fresh-only preflight rejects.  Reflash is the current recovery.  A
future reusable image pipeline should add a durable resumable transaction before
claiming in-place retry after arbitrary interruption.

The stock SSH daemon still advertises password and keyboard-interactive methods.
The new tooling refuses those methods, so this does not weaken the cutover path,
but disabling them globally would reduce the phone's existing attack surface.
That is deferred because graphical replacement does not authorize changing the
operator's recovery service.

The minimal PAM session, Alpine package snapshot behavior, headless and DRM
Sway commands, narrow polkit policy, and supervised recovery have now been
proven against the phone's installed systemd, PAM, APK, and wlroots versions.
The RCU trace proves that retiring a BPF program can hang this kernel, but the
quiet plugged-in failure proves that avoiding the two known per-session BPF
producers is not sufficient.  Those results stopped further work on v26.06 and
triggered the known-stable-kernel comparison.  They are not instructions for
the current v25.06/OpenRC image.

The v25.06 image now has a stable plugged-in minimal UI, real touch keyboard,
native Firefox, on-demand vanilla Android, and handset audio devices.  Pierre's
hands-on plugged test is next.  When he returns, run the unplugged awake-idle
and suspend/resume gates, then turn on and validate the modem only with him
present.  Third-party Android APKs remain blocked on a restrictive guest
network policy; telephony and the polished Assist home remain deferred until
the physical acceptance gates pass.

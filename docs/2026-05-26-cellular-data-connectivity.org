#+title: Cellular Data Connectivity: SIM7600G-H 4G HAT, NetworkManager, Wifi↔Cell Failover
#+date: 2026-05-26

The "Cellular modem" item under *Actual phone build* in [[file:../roadmap.org][roadmap.org]],
scoped to the *data-connectivity* milestone: bring up a Waveshare
SIM7600G-H 4G HAT so the phone has a working cellular IP + default
route, and falls over automatically between home wifi and cellular.
This is what lets you take the phone out of the house and keep a live
internet connection — the foundation every later cellular feature (SMS,
voice) and the away-phone WireGuard work build on.

*Scope note (2026-05-26):* this PR also lands the on-device *network
status + control* surface — a tappable cell/wifi modeline indicator and a
=*network*= control page (toggle cell/wifi, pick a wifi network).  That was
originally deferred to the *Modeline status bar* item (Decision 6), but
pulled in at the user's request so the cellular work is *visible and
controllable* on the phone, not invisible plumbing.  See Decision 6 for the
design and the one piece still deferred (a protected credential-entry flow for
a *new* secured wifi password, including digits and symbols).

The reference for "get this going" is the OURS project (a DIY Pi phone
on the same SIM7600 module).  We borrow its *shape* — AT-command modem,
NDIS-style data interface, an idempotent bring-up — but *not* its
mechanics: OURS ran a Pi 3B with a vendor =simcom_wwan.ko= replacing the
in-kernel driver, raw =AT$QCRMCALL= + =udhcpc=, and an =@reboot= cron to
re-establish it all.  On current Raspberry Pi OS that stack is obsolete;
the in-kernel =qmi_wwan= driver + ModemManager + NetworkManager do the
same job with autoconnect persistence and no cron.  We take the modern
path and keep the OURS recipe only as a documented break-glass fallback.

* Goal

With the SIM inserted and the HAT powered, the phone:
- registers on the carrier's LTE network and reports signal;
- obtains a cellular IP + default route via a NetworkManager =gsm=
  connection that comes up automatically on boot;
- *prefers wifi at home* and *falls back to cellular when wifi dies*,
  automatically and in both directions, without burning cellular data
  while wifi is healthy.

A successful run: with wifi switched off, =ping= and =curl= to a public
host succeed over the =wwan= interface; switch wifi back on and the
default route returns to wifi within the connectivity-check interval.

*What this milestone does NOT prove* (see Decision 1): that the phone can
reach the *home assist server* from out in the world.  That needs a
network path home — the WireGuard experiment — because the home server is
on a private LAN and, more fundamentally, the chat *back-channel* is
server→phone (=emacsclient= to the phone's daemon), which can't traverse
cellular CGNAT without the tunnel.  This doc stops at "the phone has
working public-internet data."

* Scope

*In:*
- A documented, idempotent provisioning script =deploy/cellular-bringup.sh=
  run on the phone (qmi_wwan/MM sanity checks → an =emacsos-cellular= NM
  =gsm= connection with =autoconnect= → route metrics + a connectivity-check
  stanza for failover → one-time LTE preference → bring-up + report).
- A =make cellular-bringup APN=<apn>= target that pushes the script to the
  phone, runs it under =sudo=, and removes it.  APN (and optional carrier
  auth) is operator-specific and never committed.
- A manual bring-up / validation runbook (this doc) covering the hardware
  acceptance gate, the happy-path command sequence, the failover checks,
  the =qmicli= break-glass fallback, and a debugging checklist.
- *On-device network status + control* (=network.el=): a tappable cell/wifi
  modeline segment (a global =mode-line-format=) and a =*network*= control
  page — toggle the cellular connection, toggle the wifi radio, and connect
  to a *saved* or *open* wifi network.  All reads/actions run asynchronously
  (one =make-process= reader + a sentinel; never block the main loop).

*Out (called out so they don't sneak in):*
- *Typing a NEW secured wifi password.*  Connecting to a saved/open network
  works; a new WPA network needs a protected credential-entry flow as well as
  digits and symbols.  =network.el= degrades
  to a clear note (=emacos-net--connect-kind='s =needs-password= branch is
  the single seam where the future masked-prompt lands).
- *The full =emacos-wifi-mode=* (=tabulated-list-mode=, Forget, scan refresh
  UX) — its own roadmap item.  The =*network*= page here is the lighter,
  big-button subset that fits the 320x240 touch model.
- *time / date / battery in the modeline* — the rest of the *Modeline status
  bar* item; this PR adds only the network segment, leaving the
  =mode-line-format= list extensible for those.
- *Reaching the home assist server away from wifi* — the WireGuard item
  (Decision 1, Out-of-scope).
- *SMS and voice* — separate roadmap items; they ride the same modem +
  ModemManager but a shared modem-watcher bridge is their concern.
- *A systemd unit for boot persistence* — the NM connection's =autoconnect=
  is the persistence (Decision 3).  A unit is only sketched for the
  *break-glass* =qmicli= path, which has no autoconnect.
- *Wifi connection management* (=emacos-wifi-mode=) — its own roadmap item;
  this script only nudges existing wifi connections' route metrics.

* Decisions

Numbered.  Push back on any.  Opinionated calls flagged inline.

** 1. Bound "done when" at public-internet data; reaching the home server is the WireGuard follow-up

*Opinionated.*  The user's milestone was phrased "reach the home assist
server away from wifi."  We deliberately stop short of that here, for a
reason worth stating precisely so the scope isn't mistaken for
under-delivery: cellular gives the phone a *public* IP, but the home
emacsos-server lives on a private LAN (the phone reaches it today at a
LAN address baked into =DEV_BOX_URL=).  Two paths home would be needed —
the *forward* path (phone→server =/chat=) and the *back-channel*
(server→phone =emacsclient=, via =request.client.host= in
=server/emacsos_server/phone.py=) — and the back-channel is the genuinely
hard one: it requires the *server* to initiate a connection *to* the
phone, which cellular CGNAT forbids without a VPN.  That is exactly what
the *Remote connectivity: WireGuard for the away phone* roadmap item
exists to solve.  So: this doc proves the phone has working data; the
WireGuard doc turns that into a path home.  Splitting here keeps each
diff about one thing, and means a failure in either is unambiguous.

** 2. Stack: in-kernel qmi_wwan (QMI mode, not RNDIS) + a NetworkManager gsm connection, with ModemManager owning the modem

The division of labour matters because the follow-on features depend on
it, and because the roadmap explicitly says to "prefer =ModemManager= +
=mmcli=":
- *ModemManager owns the modem.*  Registration, signal, mode/capability,
  the data bearer — and, later, SMS and voice — all go through MM
  (=mmcli= / its D-Bus API).  This honours the roadmap's preference and
  means SMS/voice won't require re-tooling.
- *NetworkManager owns the connection + routing/failover policy* and
  activates the bearer *through* MM.  An NM =gsm= connection is NM's
  front-end to ModemManager — not hand-rolled AT.
- *The kernel driver is in-tree =qmi_wwan=*, exposing =wwan0= +
  =/dev/cdc-wdm0=.  Keep the modem in *QMI* mode, *not* RNDIS/=cdc_ether=
  — RNDIS is documented to fight NetworkManager.  No vendor
  =simcom_wwan.ko= (that was OURS's Pi-3B-era workaround and is obsolete).

The NM =gsm= connection is created with =ifname '*'= — a =gsm= connection
binds the *ModemManager modem* (control plane =/dev/cdc-wdm0=), and NM/MM
choose the =wwan= data netdev themselves.  Do *not* pin =ifname wwan0=;
that is a category error for a =gsm= connection.

** 3. Boot persistence is the NM connection's autoconnect — no systemd unit

The =emacsos-cellular= connection is created with
=connection.autoconnect yes=.  NetworkManager brings it up at boot when MM
reports the modem registered — asynchronously, so it never gates wifi-first
boot.  This *is* the persistence; it replaces OURS's =@reboot= cron with
zero moving parts.  We deliberately add *no* systemd unit on this path, and
deliberately do *not* add the cell connection to any
=NetworkManager-wait-online= dependency (a slowly-enumerating modem must
not stall boot).

*The one exception, documented not shipped:* if ModemManager never
enumerates the modem (a known Bookworm risk — see Risks) you fall to the
=qmicli= break-glass path, which has *no* autoconnect.  Only there does a
systemd oneshot become necessary; the runbook sketches it.  We don't ship
it because the supported path doesn't need it and an untested unit for an
unhoped-for path is dead weight.

** 4. Failover is driven by the connectivity check (+20000), not by the metric gap

*Worth getting right — the naïve mental model is wrong.*  It is tempting
to think "wifi metric 100 < cell metric 700, so wifi always wins until
it's gone."  That only covers wifi *disconnect*.  The common real failure
is wifi *associated but dead* (captive portal, dead gateway) — the metric
gap does nothing there.  The actual failover lever is NetworkManager's
*connectivity check*: NM periodically probes a check URI per interface and,
when an interface fails, *adds +20000 to that interface's default-route
metric*.  So when home wifi goes captive, its route jumps to
=100 + 20000 = 20100=, the cellular route (700) wins, and when wifi
recovers the penalty lifts and wifi (100) wins again.

Therefore:
- The =[connectivity]= stanza (=uri= + =interval=) is *essential*, not
  decoration — it is what makes failover work at all.  (The =uri=/expected
  response may need tuning per distro; noted in the script.)
- The wifi-100 / cell-700 base metrics only decide the winner *when both
  links have connectivity* — i.e. the "prefer wifi at home" tiebreak.
- This +20000 is the *connectivity-check* mechanism and applies on QMI just
  as on PPP; it is not the separate PPP base-metric quirk.  Staying on QMI
  (=wwan=, not =ppp0=) avoids that *other* PPP penalty — a second reason to
  keep QMI mode (Decision 2).  A post-up check that the bearer is =wwan=,
  not =ppp0=, catches a mode regression.

** 5. LTE preference set once via mmcli, with a raw-AT fallback in the runbook

"Register on LTE" is part of the milestone (and 3G is being sunset in many
markets).  The script sets it via =mmcli --set-current-modes='4g'= (falling
back to =--set-current-capabilities='lte'=); this persists in the modem's
NVRAM, so it is genuinely one-time even though the script is re-runnable.
If neither =mmcli= form sticks on this firmware, the *runbook* — not the
script — has the one-time raw =AT+CNMP=38= over =/dev/ttyUSB2=, *run with
ModemManager stopped* so it isn't fighting MM for the AT port.  It is one
lever or the other, mmcli-first, never both in a run.

** 6. On-device status + control (pulled in at the user's request)

Originally this milestone shipped no elisp — the risk being "invisible
plumbing" you can't see working without a terminal.  At the user's request
we instead ship the on-device surface now, in =network.el=:

- *Tappable modeline segment.*  A global =setq-default mode-line-format= of
  =(" EmacsOS  " (:eval (emacos-net-mode-line-string)))= shows =wifi NN%= /
  =lte NN%= / =no net= on every top buffer (replacing the stock clutter; the
  =*keyboard*= buffer keeps its local =nil=).  The segment is a propertized
  string with =[mode-line mouse-1]= → =emacos-net-show=, and is wrapped in
  =condition-case= so a redisplay-time error can never brick the modeline.
  Because the modeline is a small (face-shrunk) tap target on 320x240, a big
  =("Net" . emacos-net-show)= button is also added to =emacos-global-commands=
  as the reliable entry; the modeline tap is the glance-and-go shortcut.
- *=*network*= control page.*  Shown in the top window like =*chat*=;
  rendered with the existing =emacos--btn= big buttons: a wifi on/off toggle,
  a cell on/off toggle (=nmcli con up/down emacsos-cellular= — shown only once
  the bring-up has created that connection; otherwise an honest "not set up"
  line), and a list of nearby networks that tap-connect.
- *Async + cheap.*  One =make-process= shell reader gathers all the
  =nmcli=/=mmcli= output into a delimited blob; a sentinel parses it into a
  cached =emacos-net-state= and calls =force-mode-line-update=.  A single
  =defcustom emacos-net-refresh-interval= (30s) repeat timer (lazy, hot-reload
  guarded) keeps it fresh; the timer only updates the var, redisplay does the
  rest.  A single-flight guard (=emacos-net--proc=) means reads never stack on
  the single-core Zero W.

The one piece still deferred is *typing a new secured wifi password* — that
needs protected credential entry; =emacos-net--connect-kind= is the seam, and
new-secured networks degrade to a clear on-page note rather than a doomed
=nmcli= connect that could hang on a secret-agent prompt.

** 7. Secrets flow over stdin; APN is a Make var, carrier auth is an untracked file

APN is a low-sensitivity carrier identifier, parameterised like
=DEV_BOX_URL= — a required Make var with no committed default (=make
cellular-bringup APN=<apn>=; empty = error).  Carrier *credentials*
(=APN_USER= / =APN_PASS=, rarely needed) must never ride a command line or
environment: =sudo= strips the environment by default, and anything on
argv/env is visible in the process table.  So the script reads *all*
parameters as =KEY=VALUE= lines on *stdin*, and the Make target pipes them
in (the auth lines, if any, =cat='d from an untracked =APN_AUTH_FILE=).
stdin crosses the =sudo= boundary untouched and never appears in any
process's argv/environ.  The APN ultimately lives only in the phone's own
untracked =/etc/NetworkManager/system-connections/emacsos-cellular.nmconnection=
— correct, and nothing operator-specific lands in the repo.

* Hardware acceptance gate (do this FIRST — it is not software)

None of =make test-elisp= / =make test-server= / =make smoke= can exercise
a modem; the happy path is real-phone-only.  Before touching the software,
clear these — a failure here is *not* a software bug:

1. *Power (the #1 risk — CONFIRMED on hardware 2026-05-26).*  The phone
   *resets the instant the modem's USB is plugged into the Pi* — the textbook
   brown-out signature: the modem's power-on inrush (and ~2 A TX spikes later)
   collapses the rail if it's drawing through the Pi.  Notably =vcgencmd
   get_throttled= reads =0x0= at idle (no sustained under-voltage) — so the
   problem is the *inrush at connect*, i.e. the modem being *bus-powered off
   the Pi* rather than externally.  *Fix:* power the modem/HAT from its *own*
   supply (≥2.5–3 A), so the USB link to the Pi carries data, not the modem's
   main current; keep the Pi on its own =PWR IN= feed with thick/short
   cabling.  *Diagnose:* =vcgencmd get_throttled= (bit 0 = under-voltage now,
   bit 16 = since boot), =journalctl --list-boots= / =last -x= (count the
   resets), =dmesg | grep -i volt=.  *Accept when:* plugging the modem in
   does NOT reset the Pi; =watch -n1 lsusb -t= shows the modem *stable*, not
   popping in and out.  Nothing in software can fix an under-fed modem —
   clear this gate first.
2. *Pogo-pin USB routing on THIS board.*  On a Pi Zero W the HAT is meant
   to reach the Pi's USB via spring "thimble" pins on the Zero's USB test
   pads — no cable, leaving the micro-USB OTG port free for the keyboard.
   *Accept when:* =lsusb= shows the SIM7600 with no USB cable, and the OTG
   port still drives the keyboard.  (The M2 HAT variant routes USB
   differently — verify the silkscreen.)
3. *ModemManager enumeration on this OS image.*  *Accept when:* =mmcli -L=
   lists the modem.  If not, you're on the =qmicli= break-glass path
   (runbook) and the NM-based failover here does not apply.
4. *Carrier band / LTE.*  Confirm the SIM's plan has LTE data and the
   SIM7600G-H supports the carrier's bands (it is a global LTE Cat-4
   module).  *Accept when:* =mmcli -m <idx>= shows registered on LTE.

* Wiring the modem's USB to the Pi (Zero 2 W — measured 2026-05-26)

The build is a Pi *Zero 2 W* (kernel =6.12…-rpi-v8=, 64-bit quad-core), not the
original Zero W.  The modem (a 4G/5G HAT) has its own *micro-USB device port*
*and* several *USB-A host outlets*.  Getting the USB direction right is what
makes it enumerate — an empty =lsusb= means this is wrong, and that (not the
SIM) was the real "no service" cause on first bring-up.

Rule of thumb: *USB-A = host* (downstream; you plug devices INTO it).  The modem
presents itself as a *USB device* through its *micro-USB* port.  So the link is
always *host → modem's-micro-USB*, never USB-A → USB-A.

- *Pi 3 (known-good):* modem micro-USB (device) → Pi 3 USB-A (host).
- *Zero 2 W:* the only USB *host* port is the *inner* micro-USB jack (silk
  =USB=), which the boot config already forces to host mode
  (=dtoverlay=dwc2,dr_mode=host= + =otg_mode=1= in =/boot/firmware/config.txt=;
  confirmed present).  The *outer* jack (silk =PWR IN=) is power-only.  Do NOT
  wire the HAT's *USB-A outlets* to the Pi — those are host/downstream ports,
  not the modem's device interface (this was the first-attempt mistake).
  Replicate the Pi-3 path: put a *micro-USB OTG adapter* (micro-USB male →
  USB-A female, data-capable) in the Pi's =USB= jack to get a USB-A host
  socket, then use the same modem-micro-USB → USB-A cable as on the Pi 3.  A
  data-capable micro-USB↔micro-USB cable straight into the =USB= jack also
  works (host mode is forced).  Keep Pi power on the =PWR IN= jack.
- *Power:* the modem must be *externally powered*, not bus-powered off the Pi —
  plugging it into the Pi caused an immediate brown-out reset (see the gate).

Verify from the dev box: =ssh phone lsusb= shows the modem; =mmcli -L= lists it;
=qmi_wwan= binds automatically.

* Bring-up runbook (real phone)

1. *Enumerate.*  =lsusb=; =lsmod | grep qmi_wwan=; =mmcli -L=;
   =mmcli -m <idx>= (registration + signal).
2. *Provision* from the dev box: =make cellular-bringup APN=<your-carrier-apn>=
   (add =APN_AUTH_FILE=<untracked-file>= only if your carrier needs auth).
   The script is idempotent — re-run it freely; it prints what it changed
   vs. skipped, then the active connections + routes.
3. *Done-when checks* (the two failover toggles — name them explicitly):
   - =nmcli radio wifi off= → =nmcli -t -f NAME,DEVICE con show --active=
     shows =emacsos-cellular=; =ip route= has a default via the =wwan=
     interface; =ping -c3 1.1.1.1= and =curl -sS https://example.com=
     succeed.
   - =nmcli radio wifi on= → within the connectivity-check interval,
     =ip route='s default reverts to the wifi interface (metric 100) and a
     =ping= still works.  *Both directions must pass.*

** Break-glass: ModemManager won't enumerate

If =mmcli -L= stays empty, drive the bearer directly (the OURS recipe,
modernised — note it has *no* autoconnect, so it needs the systemd oneshot
sketched below to survive reboot):
#+begin_src bash
sudo systemctl stop ModemManager
sudo ip link set wwan0 down
echo Y | sudo tee /sys/class/net/wwan0/qmi/raw_ip     # raw-ip is required ONLY here
sudo ip link set wwan0 up
sudo qmicli -d /dev/cdc-wdm0 --device-open-proxy \
     --wds-start-network="apn='<apn>',ip-type=4" --client-no-release-cid
sudo udhcpc -i wwan0
#+end_src
A oneshot =systemd= unit running the above =ExecStart= (=After=/=Wants= the
qmi device) would give it boot persistence — *only* needed on this path.

** Debugging checklist (modernised from OURS)

Power/brown-out first; NET LED state; =watch -n1 lsusb -t= stability;
=qmi_wwan= present (and *not* an RNDIS/vendor module); =mmcli -m <idx>= for
registration + signal; =nmcli con show --active= + =ip route= for the
IP/route; =journalctl -u ModemManager -u NetworkManager= for the
connection-attempt logs.  AT spot-checks (=AT+COPS?=, =AT+CSQ=, =AT+CNMP?=)
over =/dev/ttyUSB2= are last-resort diagnostics — and contend with MM for
the port, so stop MM first.

* Tests / validation boundary

State it plainly: there is no fake for a cell network in this repo, and the
provisioning script — a bash front-end to =nmcli=/=mmcli=/=lsmod= — has no
unit-test seam here (the existing tracked script, =scripts/chat-from-phone.sh=,
is itself only exercised by =make smoke='s docker round-trip).  Don't invent
a harness the milestone doesn't need.  The realistic guards are a =bash -n
deploy/cellular-bringup.sh= syntax check and =shellcheck=; everything else
is the real-phone runbook above.

The elisp (=network.el=) DOES have a unit-test seam, and =tests/test-network.el=
(wired into =make test-elisp=) covers the pure core: the terse-line splitter
(escaped colons/backslashes), the blob parser (-> =emacos-net-state= for
wifi-active / cell-active / no-net / unprovisioned), the modeline formatter +
its tap properties, the =emacos-net--connect-kind= seam, the dynamic command
set, the page render, and the single-flight refresh guard (=cl-letf=-stubbing
=make-process=, the =tests/test-chat.el= pattern).  *Real-phone-only:* the
actual =nmcli=/=mmcli= execution, the radio toggles toggling, a real wifi
connect, and the modeline *tap* on the panel.

* Risks / edge cases

- *Power brown-out* — #1 risk; a hardware gate, not a software bug.
- *ModemManager non-enumeration on Bookworm* — a documented interaction
  (a SIM-hotswap / AT-port udev rule has crashed MM on this era).  Mitigation:
  the =qmicli= break-glass path — which degrades failover to manual route
  management and needs its own persistence (Decision 3).  Also: the raw-AT
  LTE fallback must run with MM stopped, or it can be the very thing that
  destabilises MM.
- *LTE-lock not persisting via mmcli* — fall to one-time =AT+CNMP=38=;
  re-verify across a reboot in case firmware resets capabilities on power
  cycle.
- *Failover thrash* — a flaky home wifi the connectivity check repeatedly
  demotes/promotes could ping-pong the route and burn cell data.  The
  =interval= and the metric gap are the tuning knobs.
- *One USB controller on the Zero W* — host mode for keyboard + modem is
  fine; USB-gadget networking on the same port is not available
  simultaneously.  Don't let a future change assume otherwise.
- *Idempotency re-run states* — "no modem" is treated as stop-and-retry,
  never auto-fallback; =con add= is guarded by an exists-check so a re-run
  modifies rather than errors; =con up= after a modify converges the running
  state.

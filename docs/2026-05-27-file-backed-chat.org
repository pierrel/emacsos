#+title: File-Backed Chat: .assist Files as Durable Conversations on a Full-Power Emacs Backend
#+date: 2026-05-27

Today a chat is one ephemeral =*chat*= buffer backed by one fixed
server thread (=CONVERSATION_THREAD_ID=); restart loses the visible
transcript, and there's only ever one conversation.  This experiment
makes a chat a *file*: =find-file foo.assist= opens a chat surface, the
conversation persists (a thread id in the file header + the server
checkpoint), and the buffer auto-saves after each turn.  Every
conversation becomes a durable, greppable, version-controllable
artifact, and you can have many.

The unifying idea: *a conversation is a working directory plus a
backend.*  assist's =Thread= already centers on that; emacsos has been
running the degenerate case (fixed scratch dir, no real backend,
=EMACS_TOOLS= bolted on).  v1 makes the phone's emacs a real, *full-power*
=deepagents= backend (the *EmacsBackend*): it implements both the
filesystem protocol AND command execution, so the agent can *read, edit,
and run things in the =.assist='s directory on the phone* — the assist
cli/web experience, in place.

*Important framing (decided after a design pass):* the EmacsBackend is
*full-trust, not a sandbox.*  It runs commands on the phone with no
isolation.  We accept that for v1 because the phone holds nothing
sensitive yet and is single-user; real containment is a deferred
follow-up (Security, Out of scope).  This revision reflects that choice
and the design-review team's findings.

* Goal

- A =.assist= file is a durable conversation: open it → chat mode;
  SEND streams exactly as today; the file auto-saves after each turn.
- The agent can *read, edit, and run commands in the =.assist='s
  directory* — on the phone, in place, via elisp — like assist's cli in
  that directory.
- Many =.assist= buffers open at once, each its own thread; reopening a
  file the server still remembers resumes the conversation.
- The legacy ephemeral =*chat*= stays exactly as-is — the zero-friction
  scratch — alongside =.assist= for "I want to keep this."

* Scope

*In:*
- A new major mode (=emacos-assist-mode=) for =.assist= files: the chat
  surface (the *refactored* buffer-agnostic =chat.el= stream engine — see
  Decision 5), with a command surface keyed on the *mode*.
- File format: a =#+assist_thread: <uuid>= header + the =you>=/=bot>=
  transcript + any notes.  Save transcript-only, on =you>=-commit and on
  end/error/abort.  Reopen does NOT re-parse turns (Decision 10).
- Client mints a UUID per new file and sends =thread_id= on every =/chat=
  (absent ⇒ the legacy fixed id, so =*chat*= is untouched).
- Server: =/chat= keyed by =thread_id=; a new =/forget {thread_id}=
  endpoint; per-thread checkpoint.  Fixed-id =/clear= frozen as legacy.
- The *EmacsBackend* (in =emacsos-server=): implements deepagents'
  *=SandboxBackendProtocol=* — the filesystem protocol
  (=read/write/edit/ls/grep/glob=) PLUS =execute(command)= — by driving
  the phone's emacs daemon via =emacsclient=.  =execute= runs a shell
  command on the phone with =default-directory= = the working dir.  assist
  composes it into a =CompositeBackend= with =StateBackend= routing
  (Decision 9).
- *One small, generic seam in assist* (companion PR): inject a custom
  default backend.

*Out (called out so they don't sneak in):*
- *A real sandbox on the phone.*  The Zero 2 W (512 MB) can't run docker
  or the agent, so =execute= is *on the phone, uncontained.*  Real
  containment (a docker sandbox, or a capable desktop host with the
  working dir there) is the deferred path (Security, Out of scope).
- *Sync-to-server.*  Rejected; in-place elisp is simpler.
- *=#+assist_workdir:= override* — cut from v1; working dir = the file's
  directory.
- *Replaying a thread from the file transcript* when the server forgot it
  (Decision 7) — roadmap.
- *Multiple simultaneous streams.*  One at a time, server-wide, as today.
- *Retiring =EMACS_TOOLS= / migrating the legacy =*chat*=.*  The legacy
  =emacsos-phone= path stays as-is; folding =eval_elisp= into the
  EmacsBackend's =execute= is a follow-up (Out of scope).
- *Privacy/secrets* handling beyond a per-repo =.gitignore= for =.assist=.

* Decisions

Numbered.  Push back on any.  Opinionated calls flagged inline.

** 1. A =.assist= file is a conversation; opening it enters =emacos-assist-mode=

=.assist= goes in =auto-mode-alist=; visiting one initializes the chat
surface over the file's content (read the header for the thread id, mark
existing content read-only, drop a fresh prompt at the end).  Coexists
with the unchanged ephemeral =*chat*=; =.assist= is the durable sibling.
*Naming:* the mode is =emacos-assist-mode= (the repo's elisp prefix is
=emacos-=, single-o; bare =assist-mode= would collide with the upstream
=assist= package).  The =.assist= extension and =#+assist_= headers are
filenames/in-file text, so they keep the product name.

** 2. One full-power EmacsBackend: filesystem + execute; the tiers collapse

*Opinionated.*  assist's =Thread= centers on a =working_dir= + a backend;
the phone's emacs becomes a real one.  The EmacsBackend implements
deepagents' =SandboxBackendProtocol=: the fs methods (=read/write/edit/
ls/grep/glob=) AND =execute(command)=.  Conceptually this *completes* the
unification — =eval_elisp= is just the backend's =execute=, and an
agent.el change is write+reload — so the old "confined file-chat vs.
trusted emacs-control" *two-tier split disappears*: the file-chat surface
is now *full-power*, the same trust level as the emacs-control path.  One
backend, one trust model.  (We don't rip out the legacy =EMACS_TOOLS= in
this experiment — see Out of scope — but they're now redundant with the
EmacsBackend and can be retired later.)

** 3. In-place via elisp on the phone — no sync, no docker; execute runs on the phone

*Opinionated.*  Every backend method runs by driving the phone's emacs
daemon over =emacsclient=: fs ops via =insert-file-contents= /
=write-region= / =directory-files=; =execute(command)= via a shell on the
phone (=process-file= / =shell-command-to-string= with =default-directory=
= the working dir, capturing exit code + output into an =ExecuteResponse=).
Each backend call is one batched =emacsclient= round-trip.

*Accepted realities:*
- *Compute is the phone's.*  The Zero 2 W (512 MB, quad A53) runs simple
  commands (git, a formatter, a small script) fine; heavy builds/tests are
  slow.  This is "edit + light run," not a build farm.
- *=execute= is uncontained* (Security): it's a real shell on the phone —
  full network, full filesystem, any binary.  Implementation hotspots are
  =edit='s exact-string-replace and =read='s =cat -n= + offset/limit over
  elisp; =execute='s exit-code/stderr capture; =grep=/=glob= as one
  batched elisp call each (deferrable to stub if slow on the phone).

** 4. Lives in =emacsos-server=, not assist — one generic assist seam

*Opinionated.*  The EmacsBackend, backend selection, =.assist= handling,
=/forget=, per-thread keying — all =emacsos-server= (+ emacsos elisp).
assist must not learn what emacs is.  unify-first needs ONE thing assist
can't do today: accept a *custom default backend.*  =create_agent= builds
the backend internally (=create_sandbox_composite_backend= when sandboxed,
else =_create_standard_backend(working_dir)= — agent.py:193-198), always a
=CompositeBackend=.  Add a way to supply the *default* backend (e.g.
=backend==) that assist still wraps with its =STATEFUL_PATHS= →
=StateBackend= routing (Decision 9) — NOT used raw.  Because the injected
default *is* a =SandboxBackendProtocol=, deepagents' =supports_execution=
turns true and surfaces the =execute= tool automatically (filesystem.py
checks =isinstance(backend.default, SandboxBackendProtocol)=).  We keep
assist's =sandbox_backend= param =None=, so its *docker-specific* code
(=container.exec_run= for research references, =hard_delete= container
teardown) stays dormant — our =execute= dispatches through the composite
default's method, no container.  Generic seam, through assist's
three-phase workflow; merges before the emacsos PR.  Research stays
enabled (a prior decision) — no sub-agent suppression seam.

** 5. Many buffers open ⇒ buffer-agnostic engine; one stream at a time

=chat.el='s stream state is *global singletons* today and the handlers
hard-code =(get-buffer emacos--chat-buffer-name)=.  Minimal correct
refactor: *de-hardcode the target buffer* (the engine inserts into "the
streaming buffer," a var set at SEND).  Because concurrency stays
*one-stream-at-a-time server-wide* (the existing global =_STREAM_LOCK=,
matching assist's web UI), the in-flight state (process, markers, timers)
is genuinely single-tenant and can stay global; only the persistent
per-file identity (=thread_id=, the file) needs to be buffer-local.  A
second SEND while any stream is in flight is refused with a hint.  This
turns =*chat*= into a degenerate one-buffer client of the same engine — a
refactor, not a fork.

** 6. Thread identity: client-minted UUID in a =#+assist_thread:= header; file is a mirror

On the first SEND in a new =.assist= the client mints a UUID, writes
=#+assist_thread: <uuid>= at the top, and *saves the file before issuing
the POST* (so a crash can't leave a checkpoint with no file pointer).
=thread_id= is sent on *every* =/chat=; absent ⇒ the legacy
=CONVERSATION_THREAD_ID= (so =*chat*= needs no client change).  The
transcript is a human-readable *mirror*; the server checkpoint is the
agent's real memory.  Hand-editing the transcript does NOT change what the
agent remembers (file = display, checkpoint = truth).

** 7. Resume: server-remembered → continue; server-forgotten → refuse

Reopening a =.assist= whose thread the server still has → resumes.
Reopening one the server has *forgotten* (wiped, =/forget='d, other
machine) → v1 does NOT reconstruct from the transcript; SEND is *refused*
with a clear note, and the file stays a readable transcript.  *Conscious
consequence:* after =/forget=, that =.assist= becomes a read-only artifact
that can't be continued until the roadmapped reconstruct lands; "new chat"
means a new file.

** 8. Working dir = the =.assist= file's directory; fs tools rooted there (a guardrail, not a boundary)

Working dir = the directory containing the =.assist= file (a phone path);
no header override in v1.  The fs methods (=read/write/edit/ls/grep/glob=)
are rooted at the working dir via =virtual_mode= (=..=-blocking), and all
=*.assist= paths are excluded uniformly (filtered from listings, refused
for read/write/edit) so the agent's *file tools* don't wander out or
clobber a transcript.  *This is a usability/accident guardrail, NOT a
security boundary* — =execute= (a shell) ignores it entirely (Security).
Per-conversation memory (=AGENTS.md=) lives in the working dir.

** 9. The backend is composed so internal scratch stays off the phone

The injected EmacsBackend must be wrapped (by assist's seam, Decision 4)
in a =CompositeBackend= that routes =STATEFUL_PATHS= to a =StateBackend=:
summarization's =/conversation_history/{thread_id}.md=, evicted
=/large_tool_results/=, and =question.txt= scratch then live in the
checkpoint (server-side), NOT written to the user's phone dir over
=emacsclient=.  Without this, every internal framework write would hit the
phone.  (This is independent of the execute decision and remains required.)

** 10. File format & save lifecycle

Header (=#+assist_thread:=) at the top, then the =you>=/=bot>= transcript;
the transient =[status]= bracket is gone by save time.  Save
*transcript-only* (the trailing =\n> = prompt is reconstructed on open),
*programmatically* (=write-region=/=save-buffer= under =inhibit-read-only=)
on =you>=-commit (with the header, Decision 6) AND on end/error/abort.
=emacos-assist-mode= disables =auto-save-mode= and blocks/aborts
=revert-buffer= while a stream is in flight.

*Reopen does NOT re-parse turns* — the =you>=/=bot>= prefixes are not
structural on reload (a =bot>= reply may contain a line starting =you>=).
On open: read =#+assist_thread:= from the top line only, mark all prior
content read-only as an opaque transcript, append a fresh prompt.  No turn
segmentation ⇒ no in-band delimiter ambiguity.

** 11. Command surface keys on the mode; no ROLLBACK in file-chat

The new branch keys on =(derived-mode-p 'emacos-assist-mode)=; the legacy
=*chat*= branch stays identity-keyed (=*chat*= has no major mode), and the
two coexist in one =emacos--top-commands= =cond=.  Distinct command names:
*New file* (open a new =.assist=; does NOT forget the current thread) and
*Forget this chat* (the =/forget= wipe).  *No ROLLBACK button in
file-chat* — ROLLBACK is tied to =apply_config=, which is a *config-repo-
specific* tool (git-committed config + one-level revert), not part of the
EmacsBackend; a general working dir's undo is its own git history + your
review, not the config rollback.

** 12. Editing while streaming = the existing marker design, buffer-agnostic

Tokens insert at a marker above the prompt; your draft input lives below
it; =save-excursion= preserves point — already how =*chat*= works, ported
buffer-agnostic so you can compose your next prompt while bot text streams
in.  A programmatic save mid-compose doesn't touch the editable region.

* Security: full-trust on-device execution (not a sandbox)

This is the consequential design choice, made deliberately.  Because
=execute= runs a real shell on the phone, *the agent has unconfined,
network-capable code execution on the device* the moment it's reading
files that might carry prompt injection.  We are NOT pretending otherwise:

- *=execute= is not contained.*  =virtual_mode= and the =*.assist=
  exclusion (Decision 8) constrain only the *fs tools*; a shell command
  ignores them — it can read anything, write anywhere, reach the network,
  and run destructive commands (=rm -rf=).  So the working-dir
  "confinement" is a guardrail for the agent's file tools, *not* a
  security boundary.
- *No safe middle on the phone.*  A real sandbox = network/fs isolation =
  docker = a capable host with the working dir there (the sync model we
  rejected).  Allowlisting commands is leaky; elisp can't be
  network-isolated in-process; a phone-egress firewall fights the phone
  wanting internet.  So it's binary: full-trust on the phone, or no
  =execute=.  We chose full-trust.
- *Why this is acceptable for v1:* the phone holds nothing sensitive yet
  and is single-user; you are the one driving the prompts; and research
  (=search_internet=) is already an accepted egress channel.  This is the
  same risk posture, extended.
- *What integrity control remains:* for *file* changes via the fs tools,
  "review the diffs" (the file-backed, git-friendly working dir).  But
  =execute= side effects are NOT a reviewable diff — that protection is
  weaker here.  Treat a =.assist= chat as you'd treat running an agent's
  shell commands on your own box.
- *Still required regardless:* the =CompositeBackend= =STATEFUL_PATHS=
  routing (Decision 9), so internal scratch doesn't leak to the phone.

*Deferred (Out of scope):* real containment for =execute= — a docker
sandbox on a capable host (the desktop variant), at which point the
working dir lives where the container is.  That's the path to a genuinely
safe surface for when the phone *does* hold sensitive data.

* Implementation sequence

0. *(companion, assist)* The generic =backend== seam: inject a default
   backend assist wraps with =STATEFUL_PATHS= routing.  Small PR through
   assist's three-phase workflow; emacsos depends on it merging first.
1. *Server thread keying.*  =ChatRequest= gains =thread_id: Optional[str]=
   (absent ⇒ legacy id); checkpointer + working dir + =THREAD_QUEUE= key by
   it; =_STREAM_LOCK= stays the server-wide single-stream gate.  Add
   =/forget {thread_id}=; freeze =/clear= as the legacy alias.
   =_build_thread= must NOT =makedirs= a phone path on the EmacsBackend
   path.
2. *EmacsBackend (=emacsos-server=).*  Implement the fs methods + =execute=
   over =emacsclient= (one batched elisp call each; =execute= = shell with
   =default-directory= = workdir, captured exit/output).  =virtual_mode=
   root + uniform =*.assist= exclusion for the fs methods.  Implement
   =SandboxBackendProtocol= (so =execute= surfaces) and verify it routes
   through the composite default, not assist's docker =sandbox_backend=
   path.  =_build_thread= for a file-chat turn injects this backend, no
   =extra_tools=.
3. *=emacos-assist-mode= (emacsos elisp).*  Refactor =chat.el='s engine
   buffer-agnostic; header read/write; save lifecycle + reopen-without-
   reparse; command surface keyed on the mode; auto-save off + revert-guard.
4. *Forget command* (=Forget this chat=) + the step-1 endpoint.
5. *Tests + smoke* (below).
6. *PR(s).*  One emacsos PR; the assist seam as its companion (merges first).

* Tests / validation boundary

- *ERT:* =emacos-assist-mode= buffer-agnostic engine (token routes to the
  right buffer); header read/write round-trip; reopen-without-reparse (a
  transcript with a literal =you>= body line round-trips intact);
  save-on-events; command-surface-keys-on-mode (both branches coexist);
  editing-while-streaming markers; revert-guard while in flight.
- *pytest:* =/chat= =thread_id= keying (+ absent ⇒ legacy id); =/forget=;
  *EmacsBackend fs guardrails* (=virtual_mode= rejects =..= for fs tools;
  all =*.assist= filtered/refused uniformly); =execute= runs with
  =default-directory= = the working dir and returns exit/output;
  =SandboxBackendProtocol= ⇒ =execute= tool surfaces; =STATEFUL_PATHS=
  route to =StateBackend=, not the phone.  *Note:* there is intentionally
  NO "execute is confined" test — it isn't (Security).
- *smoke:* a round-trip =.assist= turn against the dockerized phone — file
  written with header + transcript, a resume reads it back, and an
  =execute= turn (e.g. =ls=) runs in the working dir.
- *Real phone:* actual edit + run in a directory; multiple open buffers;
  streaming-while-editing.
- emacsos has *no small-model eval harness* — validation is tests + smoke
  + live phone.

* Open questions

1. *=working_dir= vs. =workspace_dir= vs. checkpoint.*  With
   =sandbox_backend=None=, assist derives =workspace_dir = "/"= →
   =memories_path = "/AGENTS.md"= (agent.py:186-191), not from
   =working_dir=.  Confirm the EmacsBackend's =virtual_mode= root makes
   =/AGENTS.md= resolve to the working dir on the phone, and that the
   server-side =working_dir= isn't =makedirs='d locally.  Resolve in step 2.
2. *=emacsclient= round-trip latency* for per-turn backend reads
   (=SmallModelMemoryMiddleware= reads =AGENTS.md= every turn) + =execute=
   blocking the daemon while a command runs.  Measure on the phone; long
   commands may need an async/timeout story so =execute= doesn't freeze the
   phone's emacs.
3. *Exact shape of the assist =backend== seam* (param name; bare backend
   assist wraps vs. prebuilt composite) — decided in the assist PR.
4. *Does deepagents' =execute= tool dispatch cleanly through a
   =CompositeBackend= whose =default= is a =SandboxBackendProtocol=* (vs.
   expecting assist's =sandbox_backend=)?  Verify in step 0/2 — it's the
   hinge that lets =execute= work without the docker machinery.

* Out of scope, next experiments

1. *Real containment for =execute=* — a docker sandbox on a capable host
   (the desktop variant), working dir there.  The path to a provably-safe
   surface for sensitive data.
2. *Replay/reconstruct a thread from the file transcript* — lifts Decision
   7's refusal.
3. *Retire =EMACS_TOOLS=* — fold =eval_elisp= into the EmacsBackend's
   =execute= and =apply_config= into write+reload (+ keep the config-repo
   git/rollback as a thin tool), unifying the legacy =*chat*= onto the same
   backend.
4. *=#+assist_workdir:= override*; *multiple simultaneous streams*;
   *migrating the legacy =emacsos-phone= conversation*.

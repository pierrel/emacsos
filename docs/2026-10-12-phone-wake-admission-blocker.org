#+TITLE: Phone wake admission remains blocked
#+DATE: 2026-10-12

* Known blocker

Copilot round 1 on PR 69 identified a real HIGH wake-admission race in
=44bedcac03a2d0b3591c412d400c131c126ca273=. The display owner holds
=power-state.lock= across the privileged suspend helper. An explicit =wake=
or =press= cannot advance the transition generation while that lock is held.
If its hardware event completed before the helper reads =wakeup_count=, the
sample already includes the event. The counter write can succeed and the
phone can sleep with the userspace wake callback waiting behind the lock.
This is an in-scope blocker, even though the locking order was inherited.
PR 69 must not be deployed or merged in this state. The phone remains unchanged.

* Deterministic offline reproduction

A bounded isolated Alpine container reproduced the ordering using the actual
session-power and privileged suspend helper from =44bedcac=. The fixture
substitutes sysfs paths with ordinary files; it does not exercise kernel PM.
Two test-only barriers pause the root helper before counter sampling and after
its real =mem= write. A root-owned Unix socket fixture invokes the root helper
for the service-user client, preserving the parent's actual display lock.

The controller starts suspend for the current blank generation, waits for the
before-sample barrier, increments the fixture counter from 41 to 42 to represent
an already completed IRQ, and launches an explicit wake. The actual flock
wrapper signals that wake reached lock acquisition. A separate nonblocking
flock proves the display lock is held. The controller releases counter sampling
and observes =mem= while the generation and panel state remain blank and the
wake process remains alive. Releasing the after-write barrier simulates kernel
return; only then can wake acquire the display lock and restore active state.

The reproduction succeeded. It demonstrates userspace ordering, not an actual
phone IRQ, suspend, battery result or driver lifetime. Ordinary fixture files
cannot validate the kernel's later-event rejection behavior.

* Required contract before implementing a fix

A userspace marker rechecked immediately before =mem= still leaves a window
between the check and write. It cannot fence an earlier hardware event whose
callback is delayed. A retry or shorter window does not satisfy this effort.

Linux provides kernel wake-source activation through =wake_lock= and
=wake_unlock= when =CONFIG_PM_WAKELOCKS= is enabled. A fixed privileged wake
wrapper could activate a source before waiting for the display lock and hold
it until the explicit transition finishes. This needs a bounded interruptible
counter read to avoid deadlock with the source holder, and distinct source
ownership or serialized wrappers to prevent premature release on overlapping
requests. Cleanup must release only owned sources after old processes stop.
No such mechanism is implemented here; the actual phone capability is unknown.

That guard would protect a request only after kernel activation succeeds.
Protecting an earlier hardware event throughout delayed ModemManager/Emacs
callback delivery additionally requires a verified driver wake-source lifetime
or acknowledgment contract. A sysfs interface's presence alone cannot prove it.
The kernel ABI describes the counter and wake-source boundaries:
[[https://github.com/torvalds/linux/blob/v6.13/Documentation/ABI/testing/sysfs-power][Linux 6.13 sysfs power ABI]].

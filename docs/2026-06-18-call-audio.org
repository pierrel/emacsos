#+title: Voice calls + on-device call-audio recording (validated on hardware)
#+date: 2026-06-18

This doc records what was *verified on the actual device* about placing voice
calls and capturing call audio on the emacsos phone, plus the architecture for
the eventual calling / recording / transcription features. Unlike the roadmap
items (which are intent), everything in the "Confirmed" sections below was run
live on the phone over WireGuard on 2026-06-18.

* The hardware (confirmed on-device)
- Modem: =SIMCOM_SIM7600G-H=, firmware =LE20B04SIM7600G22=, model =SIM7600G_V2.0.2=.
- HAT: the Waveshare *4G HAT (B)* variant — it carries a built-in USB hub
  (=Terminus 1a40:0101=, two external USB-A ports), an *onboard NAU8810 audio
  codec*, and a *populated 3.5mm TRRS headset jack*. Call audio is produced on
  the HAT; it does *not* travel to the Pi over USB by default.
- Board: Raspberry Pi Zero 2 W. Reached over WireGuard; the WG tunnel rides
  *wifi* (wlan0), independent of the cellular modem — so disrupting
  ModemManager/cellular does not drop access (this made the AT probing safe).

** USB serial port map (option driver, behind the HAT hub)
| Port            | Function                                             |
|-----------------+------------------------------------------------------|
| =/dev/ttyUSB0=  | DIAG (binary QCDM)                                   |
| =/dev/ttyUSB1=  | GPS / NMEA (streams =$GPGGA…=)                       |
| =/dev/ttyUSB2=  | *AT command port* — owned by ModemManager            |
| =/dev/ttyUSB3=  | silent / unused on this composition                  |
| =/dev/ttyUSB4=  | *audio PCM stream* (raw bytes, see below)            |
| =/dev/cdc-wdm0= | QMI control (data bearer; =qmi_wwan= → =wwan0=)      |

* Confirmed: voice calling works
A test call placed via ModemManager's voice API
(=mmcli -m 0 --voice-create-call="number=+1…"= then =--start=) progressed
=dialing → ringing-out → active= and rang + connected the destination phone.
No =NO CARRIER=, no VoLTE-provisioning dead end — the scenario that would have
killed the whole feature. Voice is viable on this SIM/carrier (T-Mobile).
Placing a call this way needs *no* MM disruption (no debug mode, no freed ports).
ModemManager's =voice: emergency only: no= means normal calls are permitted.

Raw AT also works (=ATD+1…;= / =ATA= / =AT+CHUP= / =AT+CLCC= / =VOICE CALL: BEGIN=)
when the AT port is free — see the port-ownership fork below.

* Confirmed: on-device call-audio recording (the key result)
The SIM7600's "USB audio" is *not* a USB Audio Class sound card — it never
appears in =aplay -l=. It is a proprietary *raw PCM stream over =/dev/ttyUSB4=*,
gated by =AT+CPCMREG=1= *after* a call connects. We recorded the far-end
(downlink) audio of a live call on the phone, fetched the WAV, and transcribed
it correctly with faster-whisper:

: "This is a test, speaking to a prototype emacs phone, hopefully to be
:  transcribed correctly. 1-2-3-4-5-6"
(Sanitized example phrase; the real test clip was transcribed accurately
except the proper noun "emacs" -> "e-max" — see the gotchas below.)

** The validated recipe
1. Place the call (=mmcli= voice API, or raw =ATD…;= on a free AT port).
2. Wait for connect: the =VOICE CALL: BEGIN= URC.  =AT+CLCC= state =0= can
   appear before USB audio is ready on an incoming call and is not a substitute.
3. =AT+CLVL=5= and =AT+COUTGAIN=8= (boost the downlink level).
4. =AT+CPCMREG=1= to start the PCM stream.
5. Read raw bytes from =/dev/ttyUSB4= (non-blocking + select).
6. =AT+CPCMREG=0,1= then =AT+CHUP= to stop + hang up.
7. Wrap bytes as a WAV, then transcribe.

** Hard-won gotchas (these were the difference between garbage and a clean transcript)
- *The PCM is 16 kHz / 16-bit / mono*, NOT the 8 kHz the SIMCom app note implies.
  Writing the WAV at 8 kHz makes it half-speed and unintelligible. Measure the
  byte rate and snap to 16000 (we observed ~16381 Hz), or set it explicitly.
- *The downlink is quiet* (raw rms ~335). =CLVL=5= + =COUTGAIN=8= help, but also
  *normalize in software* (scale peak to ~0.9 full-scale, ~×3.6 here) before STT.
- *VAD filtering is mandatory.* Without =vad_filter=True= +
  =condition_on_previous_text=False=, whisper hallucinates repeated phrases on
  pauses (an early run on near-silence produced "I'm just going to press the
  button." twice — pure hallucination).
- Proper nouns suffer on =base.en= ("emacs" → "e-max"); a larger model or a
  vocabulary/initial-prompt bias would fix it.

** AT audio commands (capability ranges read from this firmware)
| Command          | Range / value           | Meaning                                  |
|------------------+-------------------------+------------------------------------------|
| =AT+CPCMREG=?=   | =(0-1)=                 | start/stop USB serial-PCM stream         |
| =AT+CPCMFRM=?=   | =(0-1)=                 | 0=8 kHz, 1=16 kHz (one-way switch)       |
| =AT+CSDVC=?=     | =(0,1,3)=               | analog device: 0 close,1 handset,3 spkr  |
| =AT+CLVL=?=      | =(0-5)=                 | rx volume                                |
| =AT+COUTGAIN=?=  | =(0-8)=                 | output gain                              |
| =AT+CMICGAIN=?=  | =(0-8)=                 | mic gain                                 |

* Architecture
Two audio endpoints exist and are *physically separate*: the modem's call audio
(HAT codec → 3.5mm jack, or the PCM stream) vs. a USB audio dongle (a normal
ALSA card for media/TTS/STT). They do not natively unify.

- *Option 1 — serial-PCM bridge (chosen).* Keep call audio in software: read
  =ttyUSB4= for recording/STT, and (full-duplex) write uplink PCM to inject
  audio. Only path where the agent can hear/record/speak on calls and where one
  headset (the USB dongle) can serve everything. Validated for *recording*; the
  uplink/talk direction + headset are pending hardware.
- *Option 2 — analog jack (fallback).* Use the HAT's 3.5mm jack (=AT+CSDVC=1=)
  for calls; reliable, near-zero code, but two separate endpoints and the agent
  can't touch call audio. Keep as the known-good fallback.

** AT-port ownership
The successful PCM capture issued =AT+CPCMREG= on the primary =ttyUSB2=.  Live
P3 calls later proved the secondary =ttyUSB3= accepts capability queries but
rejects =AT+CPCMREG=1= during an answered call, even after =VOICE CALL: BEGIN=.
The production udev rule therefore frees both AT ports: the call bridge owns
=ttyUSB2=, while the human call UI retains =ttyUSB3=.  ModemManager keeps call
detection and data on QMI (=cdc-wdm0=), plus GPS on =ttyUSB1=.

* Speech-to-text
Validated with =faster-whisper= =base.en= on *CPU* (the RTX 3090 is occupied by
llama.cpp — only ~2 GB free), in an isolated venv. CPU is fast enough for short
telephony clips. The roadmap's plan stands: a server-side STT endpoint on the
home box; record on the phone, POST the wav, get text back.

* Update 2026-06-20: end-to-end downlink playback on a stable rail
Picked the bring-up back up on the real hardware path. Big result: *downlink
now works end-to-end* (modem PCM → =ttyUSB4= → captured → USB dongle →
headphones), on a modem that finally holds a call.

- *The power rail was THE blocker — confirmed.* Interim hookup (stand-in for the
  Pololu boost, which hasn't arrived): a *5 V USB wall charger* (sacrificial
  cable, red=5V / black=GND) feeding the HAT's *dedicated 5V/GND posts* via
  *alligator clips*; data to the Pi stays on the mini-USB "USB hub" (VBUS left
  connected — see below). With the modem on its own stiff rail, an *outbound
  call ran the full 40 s with zero re-enumeration*. The instability was the
  modem's TX-burst brownout, exactly as predicted — a hardware/power problem,
  not software. The dedicated 5V posts are *bare metal test posts* (no wire
  hole) — clip or solder to the base; the same input the Pololu will feed, so
  the wall→Pololu swap happens at the *source* end, no modem-side rework.
- *Downlink confirmed end-to-end.* Captured 10 s of a live call's downlink →
  strong signal (peak *76 %* FS, RMS ~5.7 %, ~51 % non-silent) → replayed
  through the USB dongle to headphones: *clear, correct speed*. The full receive
  path works.
- *Rate re-confirmed ~16.7 kHz.* With =CPCMFRM=1=, a 10 s capture measured
  16736 Hz (a hasty in-call 4 s measure read ~17.76 k — inflated by stream
  startup bytes; measure over a longer steady window). 16 k, never 8 k.
- *=AT+CPCMREG=1= is synchronized full-duplex — you cannot do one direction
  alone.* With it on and *no* uplink writes, the modem TX's buffer garbage (the
  far end hears "airplane-engine" static); two independent =cat=s
  (read-pipe-aplay + arecord-pipe-write) *desync* the stream → silent downlink +
  static uplink. Record-then-play sidesteps it for downlink. Real-time needs a
  bridge that keeps read+write *balanced at the modem's clock* (one process,
  matched chunks), not two loose pipes.
- *Dongle mixer resets on re-enumeration.* A USB audio dongle that re-plugs
  (e.g. during wiring) comes back with =Speaker= muted/low → silent output even
  though the PCM is fine. Re-boost =Speaker= (=amixer sset Speaker 90% unmute=)
  after any re-seat.
- *Debug gotchas that cost time:* (a) a *dead pair of headphones* read exactly
  like a software bug — silent output through a clean, signal-bearing path; a
  known-good headset isolated it instantly (test the transducer early). (b) The
  C-Media dongle is a *two-jack* type (green out / pink mic, separate); *TRRS
  earbuds in the pink jack do NOT map a mic* (3-pole jack vs 4-pole plug) — that
  was the "mic path" false-negative.
- *Uplink still pending the right hardware:* a *single-TRRS dongle* (one
  combined jack → a real mic) plus the *synchronized full-duplex bridge* above.
  Tested with EarPods-in-pink = false-negative, as expected.
- *Ops note:* WireGuard flakiness can SIGHUP a backgrounded =ssh= dial script
  mid-run (log stalls at "start", no process left). A *detached* remote process
  (=setsid=/=nohup=) survives the tunnel hiccup; poll a logfile.
- *Signal depends on placement.* Registration read 80 % at the window; moving the
  phone deeper into the house weakens it and can make calls ring out / drop.
  Reinforces the *smaller-but-better antenna* roadmap item (the bundled whip is
  bulky; an FPC/u.FL multiband LTE antenna placed well would help marginal spots).

#+TITLE: Voice-call assistant P3 — phone bridge
#+DATE: 2026-07-28

* Scope

Implement the EmacsOS client half of P3: the non-root daemon that owns one
incoming SIM7600 call, connects it to Assist's existing WSS =/call= endpoint,
and keeps serial PCM read/write balanced.  It is deployed for controlled live
validation on Pierre's phone.

* Fixed boundaries

1. The bridge is a deterministic device client.  Assist retains authentication,
   PIN, VAD, STT, TTS, and conversation state.
2. One pump reads exactly one 640-byte modem PCM frame and immediately writes
   exactly one 640-byte queued TTS frame or silence.  The modem read is the
   clock; no independent reader, writer, or timer is allowed.
   After =ATA=, the bridge waits for the modem's =VOICE CALL: BEGIN= event before
   enabling PCM.  The live modem rejects the optional gain commands on this
   path, so the bridge uses the proven =AT+CPCMREG=1= minimum.
3. The WSS client is per call.  Its secret comes only from a 0600 environment
   file, and the bridge refuses a non-=wss://= URL or absent secret.
4. Until Assist sends =answer=, no modem answer or PCM pump starts.  Once modem
   audio is ready, the bridge sends =answered= before Assist begins its PIN
   flow.  A second inbound call is ignored while the first owns the bridge.
5. Hardware adapters are narrow interfaces.  Tests use a fake modem and fake
   link to prove control ordering, fixed PCM sizing, silence-on-underrun, and
   =flush_uplink= without a modem, network, or secret.

* Delivered files

1. =server/emacsos_server/call_bridge.py=: AT, ModemManager ring subscription,
   WSS controls, jitter buffer, and the balanced pump.
2. =server/tests/test_call_bridge.py=: fakes for the modem and link plus the
   pump/control tests above.
3. =server/pyproject.toml= and =Makefile=/=deploy/= wiring: install the daemon
   and its dependencies when explicitly configured.

* Threat and liveness checks

- The bridge adds no listener and never shells out.  Caller ID and D-Bus data
  are serialized as JSON, bounded before logging, and never used as paths or
  commands.
- Only WSS is accepted.  The shared secret never appears in argv or logs.
- Queue depth is bounded and drops stale downlink, while the pump always writes
  a complete frame.  A stalled network sender cannot block modem PCM.
- Every exit closes the WSS client, stops PCM, releases ttyUSB2, and sends the
  modem hangup only for the bridge-owned call.

* Live validation

The phone now trusts Assist's local CA and the bridge reaches the server.  The
first answered call showed that =AT+COUTGAIN=8= was issued while the SIM7600 was
still connecting, so it was rejected before PCM started.  A later call showed
the gain commands remain unsupported on the automatic-answer path.  Retrying
=AT+CPCMREG=1= after =AT+CLCC= state 0 still failed: state 0 precedes the modem's
audio-ready event.  The validated hardware recipe and SIMCom's MT-call flow both
require =VOICE CALL: BEGIN= first.  The bridge now waits for that exact event,
then enables PCM once and sends =answered= only after it succeeds.  The next call
failed earlier: its initial WSS handshake timed out before Assist saw the ring,
although the authenticated path was healthy immediately afterward.  The bridge
now makes one bounded second handshake attempt while the call is still ringing.
The following call reached =VOICE CALL: BEGIN= but =AT+CPCMREG=1= still failed
on secondary ttyUSB3.  The successful hardware capture used primary ttyUSB2;
the bridge now owns that proven port while the human call UI retains ttyUSB3
and ModemManager remains on QMI.

#+title: The keyboard as a buffer-reactive touch control plane (call controls)
#+date: 2026-06-20

The keyboard window is the phone's *touch control plane*. Today it always
paints the T9 keyboard; this change makes it *reactive to the top buffer*, so a
call buffer replaces the keyboard with its own controls. First use: move the
call Accept/Decline (and a new Hang-up/Back) OUT of the call buffer and INTO the
keyboard plane.

* Principle
The bottom =*keyboard*= window is not "the keyboard" — it is *whatever touch
controls fit the thing on top*. The command-list band is already buffer-reactive
(=emacos--top-commands= dispatches on the top buffer); this generalizes that to
the *whole* surface. A buffer may declare a *keyboard plane* (a render fn); when
it is on top, the plane paints =*keyboard*= instead of the T9 bands.

This keeps the two existing actors intact: deterministic primitives
(=emacos-call=/=emacos-answer=/=emacos-hang-up=) are untouched; the plane is
pure UI wired to them.

* Mechanism (os.el)
- =emacos--keyboard-plane= — a *buffer-local* var holding a render fn (or nil).
- =emacos--render-page= reads the TOP buffer's plane (nil when the minibuffer is
  active, so prompts still get the real keyboard): plane non-nil →
  =(funcall plane)= into =*keyboard*=; else the normal four bands.
- The buffer-change follower also re-renders when the *plane* changes, not only
  the command set — two buffers can share a command set (both fall to
  =emacos-global-commands=) yet need different planes, so a plane swap must force
  a render. =emacos--last-plane= tracks it alongside =emacos--last-commands=.
- A tappable *call badge* segment is appended to =mode-line-format=
  (=emacos-call-mode-line-string=), mirroring the network segment.

* Call state + buffers (phone-call.el)
- =emacos-call--state=: nil | =incoming= | =active=.
- =*incoming-call*= buffer: top shows only "Incoming call / <number>"; its plane
  =emacos-call--plane-incoming= paints *Decline* (top) + *Accept* (bottom),
  spatially separated. Accept is *two-tap* (arms → "Confirm answer?").
- =*call*= buffer (new): top shows "Call / <status> / <number>"; its plane
  =emacos-call--plane-active= paints *Hang up* (two-tap) + *Back*.
- =Back= restores the pre-call buffer in the top window (the call keeps running);
  the keyboard reverts to T9 and the *call badge* appears in the modeline.
- The *call badge* ("● Call") shows iff =state= is =active= AND =*call*= has no
  window; tapping it re-shows =*call*=. So you can type in another buffer during
  a call and still get back to hang up.

* State transitions (D-Bus, both directions)
=emacos-call--on-call-added= registers a per-call StateChanged watch, then:
- Direction 1 (incoming) → =incoming=, show =*incoming-call*=.
- Direction 2 (outgoing) → =active=, show =*call*= ("Calling…").
=emacos-call--on-call-state=:
- 4 (active) → =active=, show =*call*= ("In progress") — covers inbound-answered
  AND outbound-connected.
- 7 (terminated) → dismiss (clear state + watch, restore pre-call buffer, kill
  call buffers, badge gone).
Belt-and-suspenders: the Accept tap also flips to =*call*= on a successful
=emacos-answer= (don't depend solely on the active D-Bus signal).

The outbound =*call*= screen is best-effort via CallAdded(Direction 2); inbound
(the explicit ask) is fully covered. =emacos-call= stays a pure primitive.

* Decisions (forks, resolved with the user 2026-06-20)
1. *Return-to-call after Back* → *tappable modeline badge* (vs. keyboard always
   showing hang-up, which would block typing during a call; vs. no return path).
2. *Hang-up* → *two-tap confirm* (matches Answer / New-chat / Forget; a mis-tap
   shouldn't drop a call).

* Test plan (ERT, tests/test-call.el)
- Plane dispatch: a buffer with =emacos--keyboard-plane= renders it; without, the
  T9 keyboard (assert =*keyboard*= contents).
- Planes render the right buttons + two-tap relabel (Accept/Confirm answer?,
  Hang up/Confirm hang up?).
- Transitions: on-call-added Direction 1→incoming / Direction 2→active;
  on-call-state 4→active(*call*) / 7→dismiss. (Updates the old
  "outgoing-ignored" test — outgoing now shows =*call*=.)
- Badge string: active + =*call*= hidden → "● Call"; else "".
- Back restores the pre-call buffer without clearing call state.

* Validated live (2026-06-20, on device over WireGuard)
Full flow works on the phone: inbound (incoming screen → Decline/Accept in the
keyboard → Accept → in-progress → Hang up/Back → Back shows the "● Call" badge →
tap to return) AND outbound. The outbound path's load-bearing assumption is
*confirmed*: =Voice.CallAdded= DOES fire for Direction-2 (=--voice-create-call=)
calls, so dialing shows the =*call*= screen with Hang up/Back.

* Known limitations / residuals (named, not papered over)
- *Stuck badge if the terminated (state 7) signal is lost while backgrounded.*
  Dismissal keys off StateChanged=7 because CallDeleted is unreliable on this
  modem.  If a backgrounded active call (you tapped Back) ends and the 7 signal
  never arrives, =emacos-call--state= stays =active= and the "● Call" badge stays
  lit.  Not fixable by construction without a poll/timeout (rejected as
  probabilistic).  Escape exists: tap the badge → Hang up → =emacos-hang-up=
  returns "no active call?" but still dismisses, clearing the state.  A
  consequence of the single-call guard: while stuck, a genuinely new call is
  ignored until the badge is cleared.  Accepted residual.
- *Outbound screen needs live verification.* The outbound =*call*= screen relies
  on =Voice.CallAdded= firing for Direction-2 (=--voice-create-call=) calls,
  which is assumed but not yet validated on device (only Direction-1/inbound has
  been exercised live).  If it doesn't fire, outbound dials get no call UI
  (hang up via =M-x emacos-hang-up=); inbound — the explicit ask — is unaffected.
  Verify on the phone before relying on the outbound path.

* Deferred
- Outbound "Calling…" cancel nuance (ringing-out vs active text) is minimal; one
  =*call*= screen serves both.
- A dedicated dial UI / contacts picker (separate roadmap items) can reuse the
  active plane.
